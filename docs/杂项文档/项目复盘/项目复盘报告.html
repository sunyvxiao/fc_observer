1.1.1　问答

Q1：经典 YAML 场景文件与 DeepAgent YAML 场景文件的异同？

A：经典场景回答"系统发生了什么"（what syscall happened），DeepAgent 场景回答"Agent 调用了什么工具"（what tool the agent invoked）。二者的设计目的，一个是为了检测项目对系统的监测，另一个是为了检测项目对 Agent 的监测。经典场景模拟的是"系统调用事实"，DeepAgent 场景模拟的是"Agent 行为意图"。

Q2：YAML 场景文件与 JSONL 事件文件的异同？

A：YAML 是场景剧本——用 delay_ms 表达步骤间的相对时序，由 VirtualClock 推进生成绝对时间戳；JSONL 是事实日志——每行自带 timestamp_ns 绝对时间戳（capabilities 中 time_source="file_timestamp"）。YAML 场景文件是"导演的剧本"——定义行为序列的意图、时序、角色和预期结局；JSONL 事件文件是"监控录像带"——只记录发生了什么事实，无意图、无预期、无角色表，但可以无限拼接、跨平台搬运、事后反复回放。前者是剧本，后者是录像带，需要一个播放器来转化。

Q3：关于播放器？

A：播放器与录像机解耦——record_from_collector() 接受任意 ICollector，同一个录像机既能录模拟剧本，也能录真实 strace/eBPF 事件，这是"真实 Agent 行为录制"的技术基础。边播放边录像——录制不是离线拷贝，而是与实时处理同源，保证"回放结果 = 实时结果"的同构性。时间维物化——VirtualClock 是转化枢纽，把相对时序烧录为绝对时间戳。容错优先——每条 flush、# 注释头、会话目录隔离，保证录像带在任何时刻中断都可读可回放。

Q4：JSONL 事件文件与 CSV 事件文件的关系？

A：前者包含后者，后者为前者的压缩。

Q5：FIFO 管道事件流的定位？

A：YAML 是上游"剧本"；JSONL 与 FIFO 是同一种数据格式（RawEvent JSON Lines 协议）的两种载体——JSONL 是"录像带"（持久化文件），FIFO 是"直播流"（一次性管道）。它是系统中唯一的实时在线输入通道，本质价值在于进程解耦——让真实 Agent 以零依赖方式把行为事件实时送进常驻的 Monitor 守护进程，是模拟系统走向"真实生产监测"的部署形态。YAML/JSONL 服务"事后"（预演/回放），FIFO 服务"当下"（实时研判+阻断）。FIFO 管道事件流是演出，JSONL 事件文件是录像，两者转化需要一个录像机。

Q6：关于录像机？

A："JSONL 可以理解为事件流（含 FIFO 流）的录像"——这个能力由两套录制机制共同实现：采集器路线——EventRecorder/SessionRecorder 把进程内 RawEvent 迭代器录成 JSONL；生产路线——monitor_daemon 的 --record 旁路录制把 FIFO 管道流直接录成 JSONL（在解析前落盘，零损失）。两者产物格式完全一致、都可回放，区别只是"录像机架设的位置"：一台在源头（采集器旁），一台在传输线上（Monitor 侧）。

1.3.1　五类捕获

1.3.1.1　程序内"播放"——文件被 Python 直接读入内存

1）YAML 场景文件 → SimulationCollector：捕获点——无捕获，是"剧本朗读"——YAML 通过 yaml.safe_load 变成 Python dict；文件发现——main.py 用 glob.glob(scenarios_dir/category/*.yaml) 批量收集。

2）DeepAgent YAML 场景 → DeepAgentCollector(simulation)：机制同 A1（yaml.safe_load → 遍历 tool_calls 序列），区别只在于构造出的 RawEvent 语义是"工具调用"而非"syscall"，且经由 AgentBridge 的映射表转换。

1.3.1.2　程序内"钩子捕获"——Hook 回调直接拦截

1）实时 Agent 工具调用 → DeepAgentCollector(live)：这是唯一事件发生在程序内部、靠注册回调捕获的通道。关键代码（deep_agent_collector.py _start_live）：Agent 在后台 daemon 线程跑，主线程只做队列消费，通过 while self._running or bridge.pending_count > 0 控制生命周期。

1.3.1.3　外部进程观测——用系统工具"旁听"真实 syscall

1）strace → StraceCollector（Linux 降级方案）：捕获点——操作系统 ptrace 机制（strace 是载体）；读取方式——subprocess.Popen + 行缓冲（bufsize=1）+ 后台读线程。

2）eBPF → EbpfCollector（Linux 首选方案）：捕获点——Linux 内核（tracepoint 全局观测，非单进程，无需 ptrace）；读取方式——perf ring buffer 轮询（用户态↔内核态共享内存环形缓冲）。

1.3.1.4　文件读取——把"录像带"读回来重放

1）文件读取（JSONL/CSV 回放）：捕获点——无，文件是之前录制的产物，读取是"纯 I/O"。与 A 类的本质区别：A 类读的是剧本（要现场构造事件），D 类读的是事实记录（直接反序列化）。

1.3.1.5　管道流——跨进程实时消费

1）FIFO 命名管道 → monitor_daemon（独立守护进程，不走 ICollector 体系）：捕获点——事件由 Agent 进程主动写入（推模型），monitor 被动接收；会话语义——Agent 断开（EOF）即会话结束 → oneshot 退出 / daemon 模式循环等待下一 Agent。

1.3.3　问答

Q1：strace（Linux 降级方案）与 eBPF（Linux 首选方案）的异同及设计目的？

A：strace 是过渡方案，eBPF 是"条件具备才启用"的终局方案；降级链 eBPF → strace → simulation 保证了系统在任何 Linux 环境都能以退一档的能力运行。

(1) 能力分层——"完整闭环"与"最小可用"：eBPF 是首选方案，是唯一能同时满足观测 + 阻断的手段。安全监测系统要落地"三级防御"（L2 越界阻断、L3 攻击终止），必须在 syscall 入口处拦截，这只有 eBPF 能做到，所以 eBPF 承载了系统的最终形态。strace 是降级备选，只解决"真实观测"这一半问题，阻断返回 False 并明确提示"请使用 eBPF 模式"；其定位是快速建立真实数据通道，让 observer_core 的规则/研判/审计链路先跑在真实 syscall 数据上。

(2) 环境兼容性兜底——eBPF 的苛刻前置条件：eBPF 需要内核 ≥ 5.x 且带 BTF、libbpf ≥ 1.4 已安装、进程有 CAP_BPF/CAP_PERFMON、字节码已预编译。真实部署中这四条任何一条不满足（旧内核、无特权容器、未编译字节码）eBPF 就起不来。strace 几乎在任何 Linux 上都存在且部署成本为零。_check_ebpf_capability() 的存在证明设计者明确意识到了这一点。

(3) 渐进式开发路线的载体：回顾项目文档中的开发排期（eBPF 开发计划），路线是"先 strace 打通链路 → 再 eBPF 补齐阻断"。strace 实现简单（一个 subprocess + 几个正则），可以最快验证"真实进程 → RawEvent → observer_core"整条链路；eBPF 实现复杂（ctypes 绑定、字节码编译、ring buffer、kprobe 生命周期管理），适合在链路已被验证的基础上迭代。两者共用 ICollector 接口，意味着上层代码一行不用改——这正是抽象接口设计价值的最直观体现。

(4) strace 的独立教学价值：项目是"模拟学习系统"（教学演示定位）。strace 的文本输出可读性极强——学生可以直接看到 execve("/bin/ls", ["ls", "-la"]) = 0 这样的原始 syscall 行，理解"观测→解析→事件化"的完整过程；而 eBPF 是二进制 ring buffer，对学习者而言是黑盒。strace 保住了"白盒可理解性"这条产品线。

Q3：该方案能成功接入市面上大多数生产级 Agent 吗？生产可用性如何？

A：评估结论——方案能成功接入市面上大多数生产级 Agent，但有一个定位需要修正：

(1) C 档（Hook）从"可选通道"升级为"主通道"：因为主流 Agent 全都有 hook，且语义同构。项目现有的 HookRegistry 设计（YAML 驱动、capture_mode、param_rules）与业界实践完全吻合，落地优先级应大幅提升（当前它还停在未接线的半成品状态）。

(2) A 档（eBPF）从"备选"升级为"安全底线"：hook 可被配置禁用、可被恶意 Agent 关闭，eBPF 内核观测是唯一不可绕过的通道——混合监测的"校验"意义比此前评估的更大。

(3) MCP 通道定位为辅助：标准化程度最高、一次适配多家复用，但依赖 Agent 主动调用，只适合做补充上报。

(4) 需要补一个"适配器生命周期管理"：各框架 hook 格式演进快（Codex 三个月三次大改版），YAML 里的 version 字段应配合"过期检测 + 升级提示"机制。

1.4　发现的缺陷以及改进方向

1.4.1　混合监测逻辑改进

基于前几轮复盘暴露的短板（eBPF 归属缺失、strace 可感知、FIFO 有侵入），互补方案的核心思想是："内置上报定归属，外部观测做验证，上报引导过滤，双向交叉校验"。

关键改进点（按优先级）

(1) 补上 eBPF 的归属过滤（最高优先级，前几轮已确认是欠账）：在 observer.bpf.c 观测探针中增加 target_pid map 查询（模式照抄已有的 block_policy kprobe 逻辑），未命中即 return 0 不上报；数据源——由 monitor_daemon 在收到 FIFO 上报的第一条事件（含 pid 字段）时写入该 map（上报引导过滤）；备选维度——事件结构体已有 uid 字段，支持按 UID 过滤（同 UID 多进程场景）。

(2) 双源事件流的关联与交叉校验（核心增值能力）：关联键——pid + 时间窗。FIFO 工具级事件（"调用了 execute"）应与 eBPF syscall 级事件（"execve 发生"）在时间上对应。不一致场景 = 高危信号：Agent 上报"只读了文件"，但 syscall 显示有 O_WRONLY 写入 → 上报伪造；syscall 事件无对应工具调用 → 绕过上报的隐蔽行为（Agent 被攻击后自行执行命令）。这是"无感监测"与"可信监测"的结合点：解耦不意味着只信一头。

(3) 阻断能力借道 eBPF：FIFO/Hook 上报发现越界 → 研判层发 Command → 经 ebpf_command_sender 更新 block_policy map → kprobe 返回 EPERM；strace 环境则降级为"仅告警"（其能力边界已明确）。

(4) 降级链保持三级可用性：eBPF+FIFO（完整：观测+校验+阻断）→ strace+FIFO（观测+校验，无阻断，ptrace 可感知风险提示）→ 仅 FIFO（最小可用：有归属、无 syscall 佐证）。

改进方向不是"选一种"，而是把 FIFO/Hook 当作 Agent 的身份声明层、把 eBPF 当作事实校验层：用上报解决归属、用内核观测解决信任、用交叉校验把"Agent 声称的行为"与"系统记录的行为"对齐——不一致就是风险。补齐 eBPF 的 PID 过滤是打通这条互补链路的第一步，也是最关键的一步。

1.4.2　Agent 通用接口改进

项目中已经有为通用接入设计的组件，但尚未接入主链路。

成为通用监测系统的关键改进（按优先级）

(1) 落地 HookRegistry：AgentBridge 的硬编码 _tool_map 改为从 registry 加载，让"加框架不改代码"真正成立。

(2) 建立 hook_configs/：先把 pydantic-deep.yaml 补上作为第一个样例（把现有 40+ 映射迁入 YAML）。

(3) 定义 FrameworkAdapter 协议：标准化"框架 Hook 事件 → RawEvent"的翻译层，每个新框架只写翻译逻辑。

(4) MCP 通道：实现 MCP Server 包装（PRD 里提过的 MCP 透明代理），让 Codex、Claude Code 等支持 MCP 的 Agent 走统一标准接口。

2.3　发现的缺陷以及改进方向

2.3.1　处理机器的合并

必要性评估：中等偏低

(1) 机器数量多 ≠ 复杂度高。系统的真实复杂度来源是 6 种采集模式（业务需求）和三级阻断语义（安全需求），而不是机器数量。合并机器不减少业务复杂度——所以"为精简而合并"没有必要。

(2) 重复代码的实际体量：B/C/D 三处重复各约 30-80 行，总计 200 行左右，在一个 2.6 万行的项目中占比 <1%。不改也能运行，改了是工程卫生问题而非正确性问题。

(3) 教学项目的特殊性：每台机器独立成文件、命名直观（"录像机""播放器""审计员"），本身就是教学资产——白盒可读性是设计目标之一。激进合并（比如把五组合成两三个大模块）会损害这一目标。

有共性、有合并空间，但合并的正确姿势是"抽骨架"（基类/编排器）而非"减机器"。必要性中等：建议做 B 的基类抽取和 D 的 Pipeline 编排器两处（预防链路分叉风险是真正的理由），C 可做可不做；核心 9 台机器和 6 个采集器的独立性应当保持——它们的存在是架构意图，不是冗余。

如果要做，优先级排序：D（Pipeline 编排器）> B（QueuedCollectorBase）> C（RawEventFactory）——因为 D 防的是"链路分叉"这一真实风险，B 防的是"三处同改"，C 只是消除小重复。

2.3.2　长期日志维护方案

高必要性，生产落地的前提

该改进使系统能够实现对 Agent 的长期维护，并识别"分散式串谋攻击"。依赖关系：T1/T2/T3 可并行（地基）→ T4 完成后 T5（片段扩展）→ T6/T7/T8（rollup 与挖掘，依赖 T4/T5）→ T9/T10/T11（与阶段二可并行，最终合并调参）→ T12（收尾）。核心设计红线（贯穿所有 todo 的约束）：异常明细全保留、指纹边全透传、L0 永不删除——这是"压缩计算量"与"保住攻击链重建能力"的平衡点，任何一项实现都不能违反。

阶段一：地基加固——L0 与数据指纹（先决条件）

T1. 新增数据指纹追踪模块：目标——实现文件内容指纹（哈希）+ 敏感标签的污点传播（taint），让跨 Agent、跨时间的攻击链靠数据血缘而非时间窗口维系。改动——新建 observer_sim/observer_core/monitoring/fingerprint_tracker.py；在归一化管线 file_open(read) 事件上打指纹、file_open(write) 继承上游标签、net_conn 携带标签检查。验收——m05 场景（4 小时间隔跨 Agent 外传）能被指纹关联识别，输出完整攻击链。

T2. BehaviorGraph 时间分桶索引（消除 O(n²)）：目标——把 _detect_cross_agent_edges 的全量遍历改为按时间戳分桶（1 秒/桶），只查相邻 2~3 个桶，并支持无时间限制的指纹边。改动——observer_sim/observer_core/audit/behavior_graph.py。验收——百万节点规模下每条事件的 cross_agent 检测耗时从 O(n) 降为 O(窗口)，新增 fingerprint 边类型。

T3. L0 原始流水保留策略：目标——AuditLogger 按天分文件 + 保留期配置（默认 90 天），确立"L0 是事实来源、永不删除"的原则。改动——observer_sim/observer_core/audit/audit_logger.py、config.yaml（新增 retention_days）。验收——L0 文件按天滚动，保留期内任意 entry_id 可下钻还原原始事件。

阶段二：分层滚动摘要金字塔（核心）

T4. 修复 ReportCacheManager 的 GC 缺陷：目标——片段超过 60 段上限时不再直接删除，而是先 rollup 为 L2 小时日志再清理。改动——observer_sim/observer_core/audit/report_cache.py 的 _gc_segments。验收——旧片段删除前必有对应 L2 日志存在，数据无丢失。

T5. L1 片段格式扩展（不对称概括）：目标——片段在现有 stats + entry_ids 基础上新增"异常明细区"（ALERT/BLOCK/高分事件的完整字段+决策链）和"指纹边区"（全量透传，不聚合）。改动——report_cache.py 的 _generate_segment、merge_segments 透传新区。验收——异常明细与指纹边从 L1 一路透传到 L3，任一时刻不丢失。

T6. L2 小时日志生成器：目标——每小时以 60 个 L1 片段为输入做小时级审计——分钟级序列模式检测、违规累计与升级、指纹关联分析，产出 L2 小时日志。改动——新建 observer_sim/observer_core/audit/rollup_engine.py（L1→L2 rollup）。验收——L2 日志能重建小时级攻击链；计算量 = O(60 片段) 而非 O(60N 事件)。

T7. L3 天级审计引擎：目标——每天以 24 个 L2 日志为输入做天级审计——基线漂移检测（CUSUM）、跨 Agent 串谋全图分析，产出天级深度报告。改动——rollup_engine.py（L2→L3 rollup）。验收——长期分散蓄谋攻击（小时~天级间隔）在天级审计中被检出。

T8. 实现 evolution 预留接口（模式挖掘闭环）：目标——实现 IPatternMiner（PrefixSpan/马尔可夫链挖掘攻击序列模式）+ IStrategyGenerator（挖出的模式生成 YAML 规则回喂 RuleEngine），挂接在 L3 天级审计执行。改动——新建 observer_sim/evolution/pattern_miner.py、strategy_generator.py；evolution/interfaces.py 不变。验收——m05 类攻击被挖掘为规则后，下次实时运行可被 RuleEngine 直接拦截（闭环验证）。

阶段三：窗口分层与慢速检测（准确性）

T9. 分层窗口参数化：目标——把单一窗口（10 条/60 秒）拆为热窗口（秒~分钟，序列检测）、温窗口（15~30 分钟，聚合特征）、冷窗口（天级，基线漂移），全部进 rules/tuning.yaml 热加载。改动——event_normalizer.py、tuning.yaml（新增 windows 配置节）。验收——三类攻击（突发/链式/分散）各有匹配的检测窗口，参数改后无需重启生效。

T10. 时间衰减累加器（慢速违规积分）：目标——新增小时级半衰期的风险积分累加器，捕获"每步都低于阈值但持续累积"的慢速攻击；与现有 5 分钟快窗（AgentViolationTracker）构成双速计数。改动——新建 observer_sim/observer_core/judgment/decay_accumulator.py，接入 RiskScorer 输出。验收——轻微可疑行为（单步 <0.1 分）持续累积后能触发关注告警，正常行为积分自然衰减归零。

T11. 场景基准集参数标定：目标——用现有 40+ 场景（normal/anomalous/boundary/multi_agent/extreme）做参数扫描基准——对攻击场景测检测延迟、对 normal 场景测误报率，画权衡曲线定参数。改动——新增 observer_sim/tests/benchmark_window_tuning.py（或 scripts 目录）。验收——产出一份参数标定报告（各窗口大小 + 延迟/误报数据），作为 T9 参数默认值依据。

阶段四：报告输出联动（收尾）

T12. 三级报告输出体系：目标——L1 分钟简报（自动片段）、L2 小时摘要（export_from_segments 已有雏形）、L3 天级深度报告（含攻击链重建 + 挖掘出的新模式 + 处置建议）三级联动输出。改动——report_exporter.py 扩展天级报告模板；monitor_daemon.py 挂接 rollup 调度。验收——三种报告按各自周期自动生成，天级报告可从聚合异常下钻到 L0 原始事件。

2.3.3　多层安全机制升级【大方向一】

方向定位：实时环的能力扩展。在现有"规则引擎 + 四维评分"基础上，新增覆盖四个攻击复杂性维度（多步、跨主体、跨时间、隐蔽）的检测层。贯穿原则：每层保持确定性、单事件 O(1)~O(窗口)、毫秒级、可复现审计，不引入 LLM。

T1. 稀有度评分层（覆盖"未知单步攻击"）：把基线"见没见过"的二值判断升级为连续稀有度评分（TF-IDF 式频率分布），信号并入 D2 基线分。攻击对策：伪装成正常命令的低频高危行为组合。

T2. 序列状态机层（覆盖"多步链式攻击"）：新增轻量状态机模块，只跟踪高危状态转换（如 sudo → 写 authorized_keys → ssh 登录），不做规则化组合匹配。攻击对策：m04 类权限提升链、多步攻击链。

T3. 数据血缘层（覆盖"跨主体 + 跨时间攻击"，核心）：实现文件内容指纹 + 敏感标签的污点传播（A 读敏感 → 写中转 → B 读中转 → 外联），在 BehaviorGraph 增加无时间限制的 fingerprint 边。攻击对策：m05 类分散蓄谋、m02 类跨 Agent 串谋。

T4. 时序漂移层（覆盖"慢速累积攻击"）：新增小时级半衰期风险积分累加器 + CUSUM 基线漂移检测，与现有 5 分钟违规快窗构成双速计数。攻击对策：每步低于阈值但持续累积的慢攻击。

T5. 分层窗口参数化（支撑 T1~T4 的时间基础）：把单窗口（10 条/60 秒）拆为热/温/冷三层窗口，全部进 tuning.yaml 热加载；用 40+ 场景基准集扫描标定参数。

T6. 图谱性能治理（消除实时路径的 O(n²)）：BehaviorGraph 时间分桶索引替代全量遍历、节点落盘与内存热区间、基线 set 上限（LRU）、进程树 GC。意义：多层机制叠加后，实时路径仍保持可扩展。

T7. 交叉验证闭环（覆盖"主动隐蔽"）：补上 eBPF 观测探针的 PID 过滤，实现"上报引导过滤 + 双源比对 + 不一致告警"的声明-验证-阻断闭环。攻击对策：黑盒 Agent 不上报、清除痕迹的隐蔽行为。

依赖与优先级：T5（窗口基础）+ T6（性能基础）→ 先行，其余层的承载地基；T3（数据血缘）→ 优先级最高，弥补分散蓄谋/串谋的最大盲区；T1/T2/T4 → 可并行推进；T7 → 依赖混合监测架构现状，最后收口。

2.3.4　Agent 辅助自进化【大方向二】

方向定位：离线进化环的实现。把"从历史行为中自动学习新的威胁定义"落地为一条流水线：确定性统计挖掘先筛候选 → 内置 agent 做语义解释与规则生成 → 产出回喂实时层。贯穿原则：agent 永不直接处置，只产出规则建议与分析报告；实时环确定性不受 agent 可用性影响。

T8. ITraceStore 落地（追踪数据存储，地基）：实现 ITraceStore 接口——将每个事件的处理链路（TraceRecord）持久化，支持按 agent/事件类型/风险等级/时间范围查询。意义：为挖掘和回测提供统一数据源；实现可选 SQLite（起步）或时序库（规模化）。

T9. L1/L2/L3 分层滚动摘要（agent 的输入基础，地基）：落地三级日志金字塔——L1 分钟片段（含异常明细+指纹边）→ L2 小时日志 → L3 天级聚合；修复 ReportCacheManager GC 缺陷（rollup 后再删），L0 原始流水按保留期留存。意义：把全量数据压缩到 agent 可消化的规模。

T10. IPatternMiner 实现（统计挖掘先行）：实现确定性模式挖掘——序列模式挖掘（PrefixSpan/马尔可夫链）+ 频率异常检测，从 L3 数据产出候选异常模式列表。原则：统计先筛、agent 再判。

T11. 内置分析 agent（LLM 语义层）：实现离线分析 agent，输入 = 候选模式 + L3 聚合数据 + 行为图谱快照，输出三类：①候选模式的语义解释 ②YAML 规则草稿 ③攻击链解读报告。实现基础：复用项目已有 LLM 生态（AgentBridge、deep-agents-demo）。能力边界：只读分析 + 产出建议，无任何处置接口。

T12. IStrategyGenerator 的 agent 实现（规则生成与格式化）：把 agent 生成的规则草稿结构化为 RuleEngine 可加载的 YAML（校验 rule_id/priority/action/match_mode/patterns 等字段合法性），实现 export_to_yaml。衔接：生成物进入方向三的验证闸门，而非直接上线。

T13. 回测验证器（进化链的必要环节，衔接方向三）：在历史数据上回测候选规则，计算 false_positive_rate / false_negative_rate（ValidationResult 字段已预留）；超阈值即拒绝上线。意义：这是"agent 辅助自进化"与"验证闸门"两个方向的交汇点，也是幻觉兜底的第一道防线。

T14. 进化调度器（编排收口）：把 L3 天级审计 → 挖掘 → agent 分析 → 规则生成 → 回测 → 人工审核队列编排为每日自动流水线。验收：每天自动跑一轮完整进化流水线，产出"候选规则清单 + 天级深度报告"。

依赖与优先级：T8 + T9（数据地基）→ 并行先行；T10（统计层）→ 依赖 T8/T9；T11/T12（agent 层）→ 依赖 T10；T13（回测）→ 与 T11/T12 衔接，属方向三；T14（调度）→ 最后收口。

2.3.5　验证闸门与人工审核【大方向三】

方向定位：双环之间唯一通道的安全阀。所有离线环产出（agent 生成的规则、挖掘出的模式）在进入实时环之前，必须经过"自动回测闸门 + 人工审核"两道关卡。贯穿原则：离线产出未经闸门绝不可能影响实时判定；agent 永不直接处置。这是整个自进化体系"可信"的根本保障。

T15. 回测执行器（验证闸门核心）：实现候选规则的自动回测——复用项目现成的场景回放基础设施（SimulationCollector 回放场景库）：用 normal 场景测误报率、anomalous/multi_agent 场景测漏报率，计算 ValidationResult 已预留的 false_positive_rate / false_negative_rate / tested_traces。意义：40+ 场景库天然构成回测基准集，无需另建测试数据。

T16. 阈值闸门与分级处理（幻觉第一道兜底）：定义上线门槛（如误报率 ≤ X% 且漏报率 ≤ Y%，阈值进 tuning.yaml 可配）；回测结果三档分流——通过 → 进入审核队列；临界 → 标红人工复核；拒绝 → 归档留痕。意义：agent 产生幻觉时，坏规则在此被确定性拦截。

T17. 规则版本管理与热加载上线（含回滚）：规则库版本化——default_policy.yaml 已有 version 字段与 change_summary 变更记录机制，扩展为：审核通过的规则合并入规则库、版本号递增、热加载生效；新增一键回滚——新规则上线后若线上误报率异常上升，回退上一版本。意义：让"上线"可逆，人工审核的决策压力因此可控。

T18. 人工审核工作台（人是最终责任人）：审核队列接口/界面，每条候选规则展示三件套——规则草稿 + 回测报告（两项比率+命中样例）+ 攻击链证据（可下钻到 L0 原始事件）；审核状态机 pending → approved / rejected，所有审核决策留痕（谁、何时、依据什么批准）。意义：人工审核不是橡皮图章，而是依据证据的决策。

T19. 双环安全阀的架构级硬约束（贯穿所有环节）：架构层面封死旁路——①agent 模块只读分析、无任何处置接口；②离线环产出物的唯一出口是 T16+T18 组成的闸门；③实时环代码中不存在任何来自离线产物的直接写入路径（用代码评审+测试固化）。验收：构造"恶意/幻觉规则绕过"测试用例，全部被闸门拦截。

依赖与优先级：T15（回测）→ 基础，先于一切；T16（阈值分流）→ 依赖 T15；T17（版本+回滚）→ 与 T15 可并行；T18（审核工作台）→ 依赖 T15/T16；T19（硬约束）→ 与 T15~T18 并行设计，最后用测试收口。

规则：15 条 → 23 条；场景：3 个 → 37 个；测试：规划单元测试 → 367 个全通过；平台：Windows 单机 → Windows/Linux 统一架构（4 种采集模式）；演示：CLI 单模式 → Web 平台（SSE）+ 交互式 CLI + 录制回放三重演示。

按需完成项

观测、阻断、审计、数据本地化四大能力均与需求严格对齐，且实现细节（研判矩阵、四级处置）比 PRD 规格更进一步。

明确缺口项（需求侧自知 + 复盘确认）

1）自进化——接口预留未实现（PRD 明示"仅定义，不实现"）→ 对应改进方向二；2）复杂攻击检测——串谋/分散蓄谋盲区（需求承诺"跨 Agent 关联检测"但窗口限制实现不完整）→ 对应改进方向一；3）生产级能力——权限管控、长期留存、内核级感知的 Windows 侧 → 对应生产模式长期规划。

结论

需求实现的主线（五大能力 × 五痛点）对齐度很高——4/5 核心能力完全落地，唯一缺口"自进化"是设计上预留而非遗漏；真正的不对齐不在"功能有无"，而在"能力深浅"：需求承诺的跨 Agent 检测、内核级感知、生产权限管控在演示级实现中打了折扣，这些正是前几轮改进方向（多层安全机制升级、双环演进、生产模式）所覆盖的——功能需求对齐分析的缺口清单与改进方向清单完全吻合，说明复盘闭环是自洽的。

4.6　录制-回放功能的设计

4.6.1　演进史实确认

这个设计在项目里是自洽的。录制-回放的起源是 PRD 降级清单第 3 项（"C++ 反向管道降级为纯 Python 模拟模式"）和 FileReplayCollector 的输入兼容。但项目描述第 9 节已经把它升级为独立功能，三个客户价值中就有"历史审计数据可回放复现，支持合规审查"——说明设计者已经意识到它不只服务于模拟。现在把它定位到"自进化 + 验证闸门"的服务层，是这条演进线的自然延伸。

4.6.2　设计合理性评估

合理，但三个用途要精确分工：

表 4-5　录制-回放用途分工

用途录制-回放的角色能否胜任
训练（自进化迭代）作为挖掘输入⚠️ 不是主输入——单个录制是一个会话序列，训练需要多个会话的聚合（这是 ITraceStore + L3 聚合日志的角色，方向二 T8/T9）。回放只能贡献"样本池"
验证（验证闸门）作为回测基准集✅ 主战场——候选规则在同一录制上回放，计算误报/漏报率；规则版本 A/B 在同一录制上回放比对判定差异，就是规则迭代的 A/B 测试
审核（人工审核）作为可复现证据✅ 但有条件——录制提供"行为事实"，审核人还要"判定依据"（为什么这样判），后者来自审计链/报告；两者合起来才是完整证据
稳定性测试作为回归基准✅ 极佳——同一录制 + 固定参数 → 判定快照逐事件比对，任何行为漂移都会现形

4.6.3　结论与改进【U 系列】

设计合理——录制-回放从"模拟降级件"演进为"验证基础设施"是标准且正确的路径，与双环架构咬合紧密：它是验证闸门（T15 回测执行器）的真实数据源、稳定性回归的 golden test 工具、人工审核的取证复现器。它能完成需求，但前提是把分工摆正：训练靠聚合（TraceStore/L3），验证靠回放（录制库），审核靠"回放复现 + 审计链依据"；同时补齐三个保真度前提（基线快照录制、时钟确定性、状态初始化），否则回放复现的判定不可信，闸门建立在失真结论上。

U10. 录制-回放验证化改造——录制格式扩展基线快照 + 回放确定性参数 + 判定快照比对器，作为方向三 T15 回测执行器的数据源基础。
