# Agent 行为监测系统 — 技术方案

---

## 一、方案概述

### 1.1 系统目标

构建一套与 Agent 进程完全解耦的行为监测系统，实现三级递进防御：

| 级别 | 触发条件 | 系统响应 | 对 Agent 的影响 |
|------|----------|----------|----------------|
| **L1 · 风险记录** | Agent 调用敏感工具或访问敏感资源 | 结构化记录事件上下文，写入审计日志 | 无感知，正常执行 |
| **L2 · 越界阻断** | Agent 试图执行越权操作 | 拦截本次调用，向 Agent 返回标准错误响应 | 收到失败码，进程继续运行 |
| **L3 · 攻击终止** | Agent 执行明确的窃密/破坏行为 | 立即终止 Agent 进程 | 进程被 SIGKILL，不可恢复 |

### 1.2 核心设计原则

- **零侵入**：Agent 代码无需任何修改，不引入监测 SDK，不注入回调函数。
- **纵深防御**：应用层（MCP Proxy）与内核层（eBPF）双层布防，互为补充，不可互相绕过。
- **策略即代码**：所有监测规则由统一的策略引擎管理，支持声明式定义与热更新。
- **语义与执行分离**：应用层探针提供框架级语义（工具名、参数、任务上下文）；内核层探针提供系统级执行事实（文件路径、网络地址、syscall 序列）。二者通过关联键（进程 PID + 时间窗）实现事件关联。

## 三、模块定义

### 3.1 M1 · MCP 透明代理（观测通道）

#### 3.1.1 定义

一个部署在 Agent 与目标 MCP Server 之间的七层透明代理，基于 JSON-RPC 2.0 协议进行双向消息转发，在转发过程中以**旁路模式**提取工具调用事件，对其进行分类标注后异步写入审计日志。

#### 3.1.2 功能

| 功能编号 | 功能名称 | 描述 |
|----------|---------|------|
| M1-F1 | 协议解析 | 识别并解析 JSON-RPC 2.0 请求/响应报文，提取 method、params、id 字段 |
| M1-F2 | 透明转发 | 将报文原样转发至目标 MCP Server，不增加延迟，不修改内容 |
| M1-F3 | 事件提取 | 从请求报文中提取 `tools/call` 类型的工具调用事件 |
| M1-F4 | 分类标注 | 根据 L1 规则对事件进行风险等级标注（info / warn / high / critical） |
| M1-F5 | 上下文注入 | 为事件附加 Agent 会话标识、任务 ID、时间戳、调用链序号 |
| M1-F6 | 异步写入 | 将标注后的事件以非阻塞方式写入审计日志存储 |

#### 3.1.3 开发目的

使系统能够在 **Agent 完全无感知** 的前提下，以 **框架级语义粒度**（工具名称、参数结构、调用序列）完整记录 Agent 的全部工具调用行为，为事后审计和行为分析提供结构化数据源。

---

### 3.2 M2 · MCP 透明代理（拦截通道）

#### 3.2.1 定义

与 M1 共用同一代理进程，在**请求转发之前**插入同步裁决逻辑。当请求被判定为越界行为时，代理**不转发该请求**，而是直接向 Agent 返回符合 JSON-RPC 2.0 规范的标准错误响应。

#### 3.2.2 功能

| 功能编号 | 功能名称 | 描述 |
|----------|---------|------|
| M2-F1 | 同步裁决 | 在转发前调用策略引擎，对工具调用请求进行同步的 allow/deny 判定 |
| M2-F2 | 请求拦截 | 当判定为 deny 时，阻止请求到达目标 MCP Server |
| M2-F3 | 错误响应构造 | 生成标准 JSON-RPC error 对象，包含预定义错误码和策略语义消息 |
| M2-F4 | 超时容错 | 当策略引擎在指定时间内未响应时，按可配置的 fail-mode（fail-open / fail-closed）执行 |
| M2-F5 | 拦截事件记录 | 将拦截事件（含判定理由）写入审计日志，与 M1 日志使用同一 schema |

#### 3.2.3 错误响应规范

```
JSON-RPC error 对象:
├── code:    -32000 (预定义的"策略拒绝"错误码)
├── message: "Policy denied: <策略名称>"
└── data:    { policy_name, reason, suggestion (可选替代方案) }
```

#### 3.2.4 开发目的

使系统能够在 Agent 执行越权操作**之前**进行拦截，阻止危险操作到达目标系统，同时**不终止 Agent 进程**——Agent 将拦截视为一次普通的工具调用失败，可自行选择错误恢复路径（重试、替换工具、向用户求助等）。

---

### 3.3 M3 · eBPF 探针子系统

#### 3.3.1 定义

一组加载到 Linux 内核中的 eBPF 程序，通过挂载到系统调用入口点（kprobe / tracepoint）来监控 Agent 进程的文件访问、网络通信和进程创建行为。当检测到 L3 级别的攻击特征时，直接向 Agent 进程发送 SIGKILL 信号。

#### 3.3.2 功能

| 功能编号 | 功能名称 | 描述 |
|----------|---------|------|
| M3-F1 | 进程标识 | 识别并标记 Agent 进程及其子进程的 PID 命名空间，确保仅监控目标进程 |
| M3-F2 | 文件访问监控 | 挂载 `sys_enter_openat` / `sys_enter_read` 等 kprobe，捕获文件路径和访问模式 |
| M3-F3 | 网络通信监控 | 挂载 `sys_enter_connect` / `sys_enter_sendto` 等 kprobe，捕获目标 IP 和端口 |
| M3-F4 | 敏感数据检测 | 将捕获的文件路径、网络地址与 L3 规则中的敏感资源清单进行实时匹配 |
| M3-F5 | 攻击模式识别 | 在 eBPF map 中维护短时间窗口的状态，检测"读取敏感文件 + 建立外部网络连接"等组合模式 |
| M3-F6 | 进程终止 | 当 L3 规则命中时，调用 `bpf_send_signal(SIGKILL)` 立即终止 Agent 进程 |
| M3-F7 | 事件上报 | 通过 perf buffer 或 ring buffer 将检测事件异步上报至用户态守护进程 |

#### 3.3.3 开发目的

提供 Agent **无法绕过**的最终防线。即使 Agent 绕过了 MCP Proxy（例如直接调用系统命令、执行内嵌脚本、通过侧信道泄露数据），eBPF 探针仍能在内核层捕获并响应。这是整个监测系统的"硬边界"。

---

### 3.4 M4 · 策略引擎

#### 3.4.1 定义

一个独立的决策服务，以声明式规则定义所有监测策略。M2（拦截通道）同步调用策略引擎进行裁决；M1（观测通道）和 M3（eBPF 探针）异步拉取规则进行本地匹配。

#### 3.4.2 功能

| 功能编号 | 功能名称 | 描述 |
|----------|---------|------|
| M4-F1 | 规则管理 | 提供规则的 CRUD 接口，支持规则优先级、分组和启用/禁用 |
| M4-F2 | 声明式策略语言 | 使用表达力足够强的策略语言——推荐 CEL 或 Rego，使每条规则可独立表达一个完整的判定逻辑 |
| M4-F3 | 同步裁决 | 对外暴露 gRPC / HTTP 接口，供 M2 同步调用，返回 allow/deny/ask 三种裁决结果 |
| M4-F4 | 规则分发 | 将 L1/L3 规则以版本化的方式推送给 M1 和 M3，支持增量更新和本地缓存 |
| M4-F5 | 热更新 | 规则变更无需重启任何监测组件，策略引擎通知各模块拉取最新规则 |
| M4-F6 | 审计追踪 | 记录每一次裁决的输入参数、匹配规则和裁决结果，写入审计日志 |

#### 3.4.3 规则分类定义

| 规则级别 | 响应模式 | 典型规则示例 | 消费模块 |
|----------|----------|-------------|----------|
| L1 | 异步 · 仅记录 | "调用 `execute_command` 工具时记录命令文本" | M1 |
| L1 | 异步 · 仅记录 | "访问 `~/.*` 隐藏文件时标注为 high" | M1 |
| L2 | 同步 · 阻断返回错误 | "拒绝访问 `http://` 非加密协议的外部 URL" | M2 |
| L2 | 同步 · 阻断返回错误 | "拒绝 `write_file` 写入 `/etc/`、`/usr/` 等系统目录" | M2 |
| L3 | 内核 · 终止进程 | "读取 `~/.aws/credentials` 并发起外网 TCP 连接 → 立即终止" | M3 |
| L3 | 内核 · 终止进程 | "尝试 `chmod 777` 修改敏感文件权限 → 立即终止" | M3 |

#### 3.4.4 开发目的

将监测逻辑与执行逻辑彻底分离。程序员在开发和维护监测规则时无需触碰代理代码或 eBPF 代码；运维人员可以针对不同环境（开发/测试/生产）部署不同的策略集合，且切换策略不需要重启任何 Agent 或监测组件。

---

### 3.5 M5 · 事件关联引擎

#### 3.5.1 定义

一个后处理服务，消费来自 M1（应用层语义事件）和 M3（内核层系统事件）的日志流，以 **进程 PID + 时间窗口** 为关联键，将框架级语义与系统级行为缝合为统一的攻击视图。

#### 3.5.2 功能

| 功能编号 | 功能名称 | 描述 |
|----------|---------|------|
| M5-F1 | 时间窗关联 | 将同一进程在 N 秒内产生的 M1 事件和 M3 事件关联为一条复合行为链 |
| M5-F2 | 语义补全 | 将 M3 捕获的裸文件路径与 M1 捕获的工具调用参数进行匹配，还原"Agent 调用 read_file 读取了 ~/.ssh/id_rsa"这一完整语义 |
| M5-F3 | 攻击链构建 | 将多条关联事件按时间序列组合为完整攻击链（如：列目录→读密钥→建立外连→发送数据） |
| M5-F4 | 告警聚合 | 同一个攻击链条内的多条 L1/L2/L3 事件聚合为单条告警，减少告警风暴 |

#### 3.5.3 开发目的

解决纯内核探针的**语义鸿沟**问题。eBPF 只能看到"进程 12345 打开了 /home/user/.ssh/id_rsa"，但无法回答"Agent 使用什么工具、在哪个任务上下文中执行了这一操作"。事件关联引擎将应用层语义和内核层事实缝合，使安全分析人员能够完整还原 Agent 的行为意图和攻击路径。

---

### 3.6 M6 · 审计日志存储

#### 3.6.1 定义

一个高写入吞吐、支持结构化查询的日志存储服务，作为所有监测事件的最终汇聚点。

#### 3.6.2 功能

| 功能编号 | 功能名称 | 描述 |
|----------|---------|------|
| M6-F1 | 结构化存储 | 以 JSON 格式存储事件，schema 统一且可扩展 |
| M6-F2 | 索引查询 | 支持按 Agent 会话、时间范围、风险等级、工具名称等维度检索 |
| M6-F3 | 保留策略 | 支持按时间和存储容量自动归档或删除过期事件 |
| M6-F4 | 输出接口 | 提供 API 供外部 SIEM/SOAR 系统消费事件流 |

#### 3.6.3 统一事件 Schema

```
{
  "event_id": "uuid",
  "agent_session_id": "string",
  "task_id": "string | null",
  "timestamp": "ISO8601",
  "source": "mcp_proxy | ebpf_probe",
  "level": "info | warn | high | critical",
  "defense_level": "L1 | L2 | L3",
  "tool_name": "string | null",
  "tool_params": {},
  "syscall_name": "string | null",
  "syscall_args": {},
  "process_pid": "int",
  "rule_id": "string | null",
  "decision": "allow | deny | kill | record_only",
  "decision_reason": "string"
}
```

## 四、模块间接口

### 4.1 接口矩阵

```
┌──────┬──────────────┬──────────────┬──────────────┬──────────────┬──────────────┐
│      │    M1/M2     │     M3       │     M4       │     M5       │     M6       │
│      │  MCP Proxy   │  eBPF 探针    │  策略引擎     │  事件关联     │  审计存储     │
├──────┼──────────────┼──────────────┼──────────────┼──────────────┼──────────────┤
│ M1/M2│      —       │      —       │ gRPC 同步裁决 │  事件流 push  │  事件流 push  │
│      │              │              │ + 规则拉取    │              │              │
│  M3  │      —       │      —       │ 规则拉取(pull)│ perf buffer   │ perf buffer   │
│      │              │              │              │  事件流 push  │  事件流 push  │
│  M4  │  规则下发     │  规则下发     │      —       │      —       │ 裁决审计 push │
│  M5  │  消费事件     │  消费事件     │      —       │      —       │ 聚合事件 push │
│  M6  │  存储事件     │  存储事件     │  存储审计     │  存储聚合     │      —       │
└──────┴──────────────┴──────────────┴──────────────┴──────────────┴──────────────┘
```

### 4.2 关键接口定义

#### I1 · 同步裁决接口（M2 → M4）

```
调用方：    M2（拦截通道）
被调方：    M4（策略引擎）
协议：      gRPC Unary
超时：      50ms（可配置）
方法签名：  Decide(ToolCallRequest) → Decision

ToolCallRequest:
  - tool_name:      string
  - tool_params:    map<string, any>
  - agent_id:       string
  - session_id:     string

Decision:
  - verdict:        enum { ALLOW, DENY, ASK }
  - matched_rules:  []string
  - reason:         string
  - error_code:     int32        (verdict=DENY 时有效)
  - error_message:  string       (verdict=DENY 时有效)
```

#### I2 · 规则分发接口（M1/M3 ← M4）

```
提供方：    M4（策略引擎）
消费方：    M1, M3
协议：      HTTP Long-polling / gRPC Server Streaming
数据格式：  JSON
版本控制：  每个规则集携带单调递增的 version 号

RuleSet:
  - version:        int64
  - l1_rules:       []Rule
  - l2_rules:       []Rule
  - l3_rules:       []Rule

Rule:
  - rule_id:        string
  - level:          enum { L1, L2, L3 }
  - priority:       int32
  - condition:      string   (CEL/Rego 表达式)
  - action:         enum { RECORD, DENY, KILL }
  - description:    string
```

#### I3 · 用户态事件上报接口（M3 内核 → M3 用户态守护）

```
通道：      Linux perf_buffer / BPF ring buffer
数据格式：  二进制结构体 (C struct)
频率：      按事件触发，非周期性

eBPFEvent:
  - pid:            u32
  - event_type:     enum { FILE_OPEN, NET_CONNECT, PROC_EXEC }
  - timestamp_ns:   u64
  - filename:       char[256]
  - remote_addr:    u32 / u128
  - remote_port:    u16
  - matched_rule:   char[64]
```

## 五、数据流

### 5.1 L1 风险记录流（异步、旁路）

```
Agent → MCP Proxy(观测) → MCP Server（正常执行，不受影响）
                │
                ▼ (旁路)
          [解析 JSON-RPC]
                │
                ▼
          [L1 规则匹配]
                │
                ▼
          [事件标注: level+rule_id]
                │
                ▼
          [M6 审计日志存储] ← [M5 事件关联引擎(异步消费)]
```

### 5.2 L2 越界阻断流（同步、阻塞）

```
Agent → MCP Proxy(拦截) ──(同步裁决)──→ M4 策略引擎
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
                 [ALLOW]            [DENY]
                    │                   │
                    ▼                   ▼
              转发至 MCP Server    构造 JSON-RPC Error
                    │                   │
                    ▼                   ▼
              Agent 正常获得结果    Agent 收到错误码
                                     (进程继续)
```

### 5.3 L3 攻击终止流（内核级、不可恢复）

```
Agent 进程 → syscall (openat/connect/sendto)
                    │
                    ▼ (kprobe)
              [eBPF 探针]
                    │
                    ▼
              [L3 规则匹配]
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
    [不匹配]                [匹配]
        │                       │
        ▼                       ▼
    允许 syscall 继续       bpf_send_signal(SIGKILL)
        │                       │
        ▼                       ▼
    Agent 正常执行           Agent 进程终止
                            ↓
                      [事件上报 perf buffer]
                            ↓
                      [M3 用户态守护] → [M6 审计日志]
```

```
┌─────────────────────────────────────────────────┐
│                   宿主机 / Pod                    │
│                                                 │
│  ┌──────────┐     ┌──────────────┐              │
│  │  Agent   │────▶│ MCP Proxy    │────▶ MCP Svr │
```

## 八、关键设计决策

### 8.1 为什么 M1 和 M2 合并在同一个代理进程中

观测通道（M1）和拦截通道（M2）共享同一个 JSON-RPC 解析器和同一个网络连接。将它们合并在同一进程中可以：
- 避免重复解析 JSON-RPC 报文
- 确保 L1 事件和 L2 裁决共用同一份工具调用上下文
- 减少网络跳数和故障点

### 8.2 为什么 L3 不依赖 MCP Proxy

eBPF 探针必须独立于 MCP Proxy 运行，因为 L3 要防御的场景恰恰包括了 Agent 绕过 MCP Proxy 的情况。如果将 L3 也放在代理层，一旦 Agent 不经过代理（例如直接执行 shell 命令、调用内嵌 HTTP 客户端、通过子进程绕过），L3 就完全失效。

### 8.3 为什么需要一个独立的事件关联引擎

M1 产生的语义事件和 M3 产生的内核事件属于两个正交的观测维度。将它们关联起来需要：
- 一个独立于实时通路的处理节点（不能阻塞 M2 的同步裁决）
- 一个能够处理乱序到达的异步事件缓冲区
- 一个专门的关联算法

因此 M5 必须是一个独立的后处理服务。
