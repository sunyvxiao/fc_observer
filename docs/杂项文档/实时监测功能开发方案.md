> **状态**：✅ 已实施完成 | **日期**：2025-08-06 | **测试**：394 passed, 3 skipped

## 一、方案概述

本方案旨在为「方寸观察者」系统增加**实时监测能力**，使 Monitor 守护进程能够旁路监测生产环境中真实 Agent 的行为，实时进行风险评分、研判决策、阻断执行，并在 Agent 会话结束后自动生成分析报告。

核心设计理念：**Agent ↔ Monitor 完全解耦，通过 FIFO 命名管道通信，无代码依赖**。

```
┌─────────────────┐     FIFO      ┌─────────────────────┐
│  Agent 进程      │──────────────▶│  Monitor 守护进程     │
│  (独立运行)      │  JSON Lines   │  (全链路 Pipeline)   │
│                 │               │                     │
│  • agent_sim.py │               │  • 事件归一化         │
│  • run_agent.py │               │  • 规则匹配           │
│  • 真实 Agent   │               │  • 风险评分           │
│                 │               │  • 研判决策           │
│                 │               │  • 阻断执行 (eBPF)   │
│                 │               │  • 审计日志           │
│                 │               │  • 报告导出           │
└─────────────────┘               └─────────────────────┘
```

## 三、技术实现路径

### 3.1 Agent ↔ Monitor 通信通道 (FIFO)

**文件**: `observer_sim/agent_fifo_writer.py`

采用 Linux 命名管道 (FIFO) 作为通信通道，Agent 端写入 JSON Lines，Monitor 端逐行读取。

**设计原则**:
- **零依赖**：仅使用 `json` + `os` + `signal`，不依赖 observer_sim 任何模块
- **非阻塞写入**：写入失败时静默丢弃，不阻塞 Agent 主线程
- **优雅关闭**：SIGTERM/SIGINT 信号处理，确保管道正常关闭
- **懒打开**：延迟到首次写入时才打开 FIFO，避免启动时序依赖

**JSON Lines 协议** — 每条事件一个 JSON 对象，字段与 `RawEvent` 兼容：
```json
{"event_id":"evt_001","timestamp_ns":1718092800000000000,"event_type":"exec",
 "pid":12345,"ppid":12300,"agent_id":"deep-agent-001","agent_framework":"pydantic-deep",
 "executable":"/usr/bin/python3","arguments":["python3","analyze.py"]}
```

### 3.2 Agent 行为捕获 Hook

**文件**: `observer_sim/adapter/agent_bridge.py`、`observer_sim/adapter/hook_registry.py`

**pydantic-deep Hook 机制**:
- 利用 pydantic-deep 框架的 `pre_tool` / `post_tool` 回调钩子
- `AgentBridge` 在工具调用前后捕获参数和结果，生成 `RawEvent`
- 通过 `HookRegistry` 从 YAML 配置加载工具名→事件类型映射规则

**Hook 配置注册表** (`hook_registry.py`):
- 从 `hook_configs/*.yaml` 目录自动发现并加载
- YAML 协议定义：`tool_mappings`（工具名→事件类型+参数映射）、`default_mapping`、`capture_mode`
- 支持扩展：新增 Agent 框架只需添加 YAML 文件，无需修改代码

**AgentBridge 双输出模式**:
- `queue` 模式：事件推入内部队列（原有行为，向后兼容）
- `fifo` 模式：事件实时写入 FIFO 管道（新增，可选）
- `both` 模式：同时输出到队列和 FIFO
- 通过 `set_output_mode("fifo", fifo_path)` 切换

**真实 Agent 集成** (`deep-agents-demo/run_agent.py`):
- 新增 `--fifo` CLI 参数
- 指定时自动创建 `AgentBridge(output_mode="fifo")`，注入 Agent hooks
- Agent 工具调用无需任何代码修改，事件自动写入 FIFO

### 3.3 阻断策略与 eBPF 集成

**文件**: `observer_sim/observer_core/blocking/ebpf_command_sender.py`

**EbpfCommandSender** — 实现 `ICommandSender` 接口的真实 eBPF 阻断发送器：

```
决策引擎判定 BLOCK → Command → EbpfCommandSender.send_command()
  → bpf_map_update_elem(block_policy, pid, flags)
  → kprobe 自动挂载（首次阻断时）
  → syscall 层拦截目标 PID
  → PID 全部解除后自动卸载 kprobe
```

**技术实现**:
- 通过 ctypes 直接调用 libbpf C 库，加载编译好的 `blocker.bpf.o`
- 操作 `block_policy` BPF map（key=pid, value=flags 位掩码）
- 动态管理 kprobe：attach 到 `sys_execve` / `sys_connect` 等关键系统调用
- 自包含设计：不依赖 EbpfCollector，仅加载阻断所需 bpf_object

### 3.4 eBPF 三级降级策略

**文件**: `observer_sim/monitor_daemon.py`

```
L0 → 正常模式: libbpf + BTF + root → EbpfCommandSender 真实阻断
  ↓ 检测失败
L1 → 重试恢复: 每 30s 周期性检测 libbpf/权限恢复
  ↓ 持续不可用
L2 → 降级模式: MockCommandSender (记录但不阻断) + 告警报告
```

**降级告警报告**:
- 格式：`output/daemon_monitoring/alerts/ebpf_degradation_{timestamp}.yaml`
- 内容：降级原因（缺 libbpf/无 BTF/非 root）、影响评估、建议操作、降级时间戳
- stderr 每 60s 输出黄色警告，提醒运维人员

### 3.5 报告生成机制

**文件**: `observer_sim/observer_core/audit/report_cache.py`、`report_exporter.py`

**D1 — 手动时间窗口查询**:
- `ReportCacheManager.query_range(start_ns, end_ns)` → 查找覆盖片段 → 合并去重
- 完整覆盖：直接合并 stats + 按 event_id 去重
- 部分覆盖：合并片段 + 从 audit JSONL 补充缺口

**D2 — 自动周期性片段**:
- 后台线程每 60s 生成一个片段 JSON
- 片段格式：`{segment_id, start_ns, end_ns, stats, entry_ids}`
- 保留最近 60 个片段（1 小时窗口），旧片段自动 GC
- 输出目录：`output/daemon_monitoring/cache/segments/`

**ReportExporter.export_from_segments()**:
- 从合并后的片段数据直接生成 Markdown 报告
- 格式与现有 `export_scenario_report()` 完全一致
- 支持指定时间范围、场景名称

### 3.6 调优参数体系

**文件**: `observer_sim/rules/tuning.yaml`、`observer_sim/observer_core/judgment/tuning_loader.py`

**tuning.yaml** — 所有可调参数的集中配置：
| 类别 | 参数 | 说明 |
|------|------|------|
| `scoring` | 维度权重、安全目录/命令 | 风险评分的各维度权重和排除列表 |
| `decision` | 阈值矩阵 | CRITICAL/HIGH 判定阈值 |
| `escalation` | 滑动窗口、累计阈值 | TIER1→TIER2→TIER3 升级参数 |
| `baseline` | 预热事件数、基线目录 | 基线学习相关配置 |
| `report_cache` | 片段间隔、最大片段数 | 报告缓存相关配置 |

**TuningLoader**:
- `get_tuning()` 单例模式，各模块运行时热加载
- tuning.yaml 不存在时自动使用硬编码默认值（向后兼容）
- 支持 `reload()` 手动刷新

**受影响的模块**:
- `risk_scorer.py` — `register_default_dimensions()` 从 tuning 加载维度权重
- `decision_engine.py` — 从 tuning 加载 `enable_auto_escalation`、`critical_score`、`high_score`
- `violation_tracker.py` — 从 tuning 加载 `window_size_ns`、`tier1/tier2_escalate_threshold`
- `baseline_checker.py` — 从 tuning 加载 `min_warm_events`、`baseline_dir`

### 3.7 稳定性测试策略

**文件**: `test.py` — 新增 `[F] 全链路验证` 选项

**测试流程**:
1. 选择历史录制会话
2. 输入回放次数 N（默认 3，范围 2-10）
3. 依次执行 N 次 `ReplayEngine.replay()`，收集统计
4. 一致性分析：逐维度比对所有 N 次结果

**验证维度**:
- **allow/alert/block 计数** — 完全一致则通过
- **max_score 偏差** — 偏差 ≤ 0.001 则通过
- **rule_hits 一致性** — 每条规则的命中次数完全一致则通过
- **events_loaded** — 加载事件数完全一致则通过

**验收标准**: 同一录制 3 次回放，所有验证维度统计完全一致。

## 七、当前模糊点与待确认事项

### 7.1 EbpfCommandSender 的 PID 来源

**问题**: 模拟场景下虚构 PID (如 60001) 无法用于真实 eBPF 阻断。eBPF kprobe 需要真实存在的进程 PID 才能挂载系统调用拦截。

**当前状态**: 模拟 Agent (`agent_sim.py`) 使用虚构 PID，仅用于 pipeline 测试。`EbpfCommandSender` 在非 root/无 BTF 环境自动降级。

**待确认策略**:
- 方案 A: `--ebpf` 模式下要求 Agent 通过 `--agent-pid <REAL_PID>` 传入真实 PID
- 方案 B: Monitor 通过 `--mode ebpf --pid <REAL_PID>` 启动时指定
- 方案 C: Monitor 自动从 strace 输出中提取真实 PID

### 7.2 手动报告的时间语义

**问题**: "查询前 N 分钟" 中的时间是虚拟时钟（`timestamp_ns`）还是真实挂钟时间？

**当前状态**: 事件使用 `timestamp_ns`（虚拟时钟），但 Monitor Daemon 在真实时间中运行。`ReportCacheManager` 当前使用挂钟时间生成片段。

**待确认**:
- daemon 模式下，虚拟时钟和挂钟的关系是什么？
- 报告查询应以哪个时间维度为准？
- **建议**: daemon 模式以挂钟时间为准（因为 daemon 是真实时间运行），模拟/回放模式以虚拟时钟为准。

### 7.3 pydantic-deep Hook 覆盖率

**问题**: pydantic-deep 框架的 `pre_tool` / `post_tool` 钩子是否覆盖所有工具调用类型？是否存在某些操作（如内部状态变更、LLM 推理过程）无法通过 Hook 捕获？

**当前状态**: `hook_configs/pydantic_deep.yaml` 已配置 20+ 种工具映射，覆盖了 execute、file_read、file_write、http_request 等主要类别。

**待确认**:
- 未覆盖的工具类型有哪些？
- 是否需要 strace/eBPF 降级采集来补充覆盖？
- 内部操作（非工具调用）是否有监测需求？

### 7.4 多 Agent 并发场景

**问题**: daemon 模式下 Monitor 通过一个 FIFO 管道接收所有 Agent 的事件。当多个 Agent 同时运行时，FIFO 的原子性如何保证？事件交错是否影响分析准确性？

**当前状态**: Monitor 通过 `agent_id` 字段区分不同 Agent，时钟推进基于全局虚拟时钟。当前设计假设单 Agent 或顺序 Agent 场景。

**待确认**:
- 是否需要多 Agent 并发支持？
- 如果需要，是否需要每个 Agent 独立的 FIFO 管道？
- 或者保持单管道 + agent_id 区分策略？

### 7.5 eBPF 阻断的 syscall 覆盖范围

**问题**: 当前 `blocker.bpf.o` 的 kprobe 挂载点覆盖了哪些系统调用？是否足以覆盖所有需要阻断的操作类型？

**当前状态**: `EbpfCommandSender` 实现了 `_ensure_kprobes_attached()` 用于自动挂载，但具体的挂载点列表需根据实际编译的 BPF 程序确定。

**待确认**:
- 需要阻断的 syscall 列表：`execve`、`openat`、`connect`、`write`？其他？
- 是否有不需要阻断的 syscall（如 `read`）？
- PID 粒度的阻断是否足够，还是需要更细粒度的过滤（如文件路径、网络地址）？
