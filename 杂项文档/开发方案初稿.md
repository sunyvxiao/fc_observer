# 方寸观察者模拟学习系统 — 开发方案

> **项目性质**：教学模拟系统 | **目标平台**：Windows | **语言**：Python（主）+ C++（探针层）| **版本**：v1.0-dev

---

## 第一部分：系统总览

### 1.1 一句话定义

模拟 Fangcun Observer「OS 层无感知采集 → 风险评分 → 分级阻断 → 链式审计 → 自进化」的完整数据管道，用 C++ 模拟 eBPF 探针层、Python 实现全部业务逻辑，在单机 Windows 环境完整复现产品核心架构，产出可观察、可调试、可修改的教学级原型。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **全链路透明** | 每个处理阶段的输入/输出均可打印、可追溯，不藏黑盒 |
| **模块热插拔** | 评分算法、阻断策略、输出格式均为可替换模块 |
| **零外部依赖** | 标准库优先，Python 仅需 `pyyaml`，C++ 仅需标准库 |
| **接口即文档** | 模块间通过明确的数据结构通信，接口定义即架构文档 |
| **教学可演示** | 预设三个场景（正常/攻击/串谋），一键运行展示全流程 |

## 第三部分：监测机制设计（重点一）

### 3.1 设计目标

> 模拟 Fangcun Observer 的「OS 层无感知采集」—— C++ 探针扮演 eBPF 内核探针的角色，捕获三类系统调用；Python 规则引擎扮演用户态策略匹配的角色。二者通过命名管道松耦合通信。

#### 3.2.1 三类探针的职责

| 探针 | 对应系统调用 | 捕获字段 | 模拟方式 |
|------|------------|---------|---------|
| **ProcessProbe** | `execve`, `fork`, `clone` | executable (完整路径), arguments (命令行参数数组), env_vars (环境变量摘要) | 接收场景事件规格，补充 pid/ppid/时间戳，构造 execve 事件 |
| **FileProbe** | `openat`, `unlink`, `rename` | file_path (绝对路径), file_op (read/write/delete/rename/chmod), file_flags (O_RDONLY 等) | 接收文件操作规格，补充进程上下文，构造文件事件 |
| **NetworkProbe** | `connect`, `sendto`, DNS 请求 | remote_addr (目标IP), remote_port (目标端口), protocol (TCP/UDP), direction (inbound/outbound) | 接收网络操作规格，补充协议信息，构造网络事件 |

#### 3.2.2 探针关键设计决策

**决策1：探针是同步阻塞还是异步非阻塞？**

模拟系统中探针为同步处理（每次处理一个事件），但 PipeWriter 设为非阻塞，避免管道满时阻塞探针。真实 eBPF 中探针是内核异步触发的，此处仅教学模拟。

**决策2：探针如何获取进程上下文？**

C++ 探针维护一个简易进程表（`std::unordered_map<pid, ProcessInfo>`），当捕获到 `execve` 事件时自动注册新进程。后续文件/网络事件通过 pid 查询进程表补充 agent_id 和 ppid 信息。

**决策3：探针如何区分不同 Agent？**

场景事件规格中携带 `agent_id` 字段。探针在首次捕获该 Agent 的 execve 事件时建立 `agent_id → pid` 映射，后续该 pid 的子进程自动继承 agent_id。

#### 3.2.3 命名管道通信协议

```
管道名称: \\.\pipe\observer_events
数据格式: 每行一个 JSON 对象，以换行符 \n 分隔

{
  "event_id": "evt_001",
  "timestamp_ns": 1718092800000000000,
  "event_type": "execve",
  "pid": 12345,
  "ppid": 12340,
  "agent_id": "code-agent-1",
  "agent_framework": "LangChain",
  "executable": "/bin/rm",
  "arguments": ["-rf", "/"],
  "file_path": null,
  "file_op": null,
  "remote_addr": null,
  "remote_port": null,
  "protocol": null
}

设计原则:
- 全量字段,缺失字段填 null (不使用 omitempty)
- event_type 决定哪些字段有效 (简化Python侧解析)
- 每行独立解析,不依赖上下文
```

#### 3.3.1 YAML 规则体系设计

规则分为**三大类九小类**，对应三种探针的捕获范围：

```
rules/
├── default_policy.yaml      # 初始预置规则（手工编写）
└── evolved_policy.yaml      # 自进化生成规则（接口预留）
```

**规则数据结构定义**：

```yaml
# 规则文件结构
version: "1.0"
metadata:
  created: "2026-01-01"
  description: "默认安全策略"

rules:
  - rule_id: "R001"                    # 唯一标识
    name: "block-dangerous-commands"   # 规则名称
    category: "command"                # 规则类别: command | file | network
    priority: 100                      # 优先级 (0-100, 越高越优先)
    enabled: true                      # 是否启用
    action: block                      # 处置动作: block | alert | allow
    description: "阻断已知高危系统命令"
  
    conditions:                        # 匹配条件
      event_type: "exec"              # 事件类型
      match_mode: "pattern"           # 匹配模式: pattern | exact | regex | path_glob
      patterns:                       # 匹配模式列表
        - "rm -rf /"
        - "dd if=/dev/zero"
        - "mkfs"
        - "curl.*\\|.*bash"           # 正则: curl xxx | bash
        - "wget.*\\|.*sh"
      context_rules:                  # 上下文规则 (可选,增强准确率)
        require_previous: null        # 不需要前序事件
        within_time_window_ms: null   # 不需要时间窗口
```

**三大类规则清单**：

| 类别 | 规则数(初始) | 典型规则 | 对应探针 |
|------|:---:|---------|:---:|
| **命令执行规则** (command) | 6 | `rm -rf /`, `curl \| bash`, `chmod 777 /`, `mkfs`, `dd`, 提权命令(sudo) | ProcessProbe |
| **文件操作规则** (file) | 5 | 敏感文件读取(/etc/shadow, .env, *.pem), 批量删除, 写入系统目录, 修改权限 | FileProbe |
| **网络规则** (network) | 4 | 外联非白名单IP, DNS查询可疑域名, 大流量外传, 非标准端口连接 | NetworkProbe |

#### 3.3.2 规则匹配流程

```
NormalizedEvent 进入规则引擎
        │
        ▼
┌──────────────────────┐
│ Step 1: 类别筛选      │  根据 event_type 过滤规则子集
│ exec→命令规则         │  只检查相关类别,减少匹配次数
│ file_open→文件规则    │
│ net_conn→网络规则     │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ Step 2: 模式匹配      │  根据 match_mode 选择匹配算法
│ pattern: 子串匹配     │  "rm -rf /" in command_string
│ regex: 正则匹配       │  re.match(pattern, command_string)
│ path_glob: 路径通配   │  fnmatch(path, "/etc/shadow*")
│ exact: 精确匹配       │  string == pattern
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ Step 3: 上下文验证    │  检查是否需要前序事件配合
│ (可选,增强准确率)     │  "读取.env后网络外传"需要两个事件
│                      │  单事件规则跳过此步
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ Step 4: 命中收集      │  按优先级排序命中规则
│ MatchResult:         │  返回最高优先级规则的动作
│ - matched_rules[]    │
│ - highest_action     │
│ - match_details      │
└──────────────────────┘
```

### 4.3 四维评分算法详解

#### 维度一：规则命中分 (Rule Match Score) — 权重 40%

```
计算逻辑:
1. 从 MatchResult 获取命中规则列表
2. 取最高优先级规则的 priority 值
3. 归一化: score = highest_priority / 100
4. 多条规则命中时加分: score = min(score + 0.1 × (命中数-1), 1.0)

示例:
- 命中 R001(priority=100): score = 1.0
- 命中 R004(priority=50):  score = 0.5
- 同时命中 R001+R003:      score = min(1.0 + 0.1, 1.0) = 1.0
```

#### 维度二：基线偏离分 (Baseline Deviation Score) — 权重 25%

```
计算逻辑:
1. 从 BaselineChecker 获取四个子维度的偏离值
2. 加权合成: 
   time_deviation    × 0.3
   + path_deviation  × 0.3
   + net_deviation   × 0.25
   + freq_deviation  × 0.15
3. 每个子维度输出 0.0(完全正常) ~ 1.0(完全异常)

基线构建方式 (模拟):
- 首次运行时无基线 → 第一个场景充当冷启动基线
- 场景1(正常开发)运行后 → 建立"正常行为"基线
- 场景2/3运行时 → 能检测到偏离
```

#### 维度三：上下文风险分 (Context Risk Score) — 权重 20%

```
计算逻辑 (模拟 Observer 的上下文关联):
1. 从 EventNormalizer 获取滑动窗口内最近 N 个事件 (N=10)
2. 检查是否存在可疑行为序列:
   - "读取敏感文件 + 网络外联" 序列 → +0.3
   - "多次权限提升尝试" 序列     → +0.4
   - "跨Agent数据流动" 序列      → +0.5
3. 最终 score = 累计加分, 上限 1.0
```

#### 维度四：序列异常分 (Sequence Anomaly Score) — 权重 15%

```
计算逻辑:
1. 维护 Agent 的"常见行为序列"模型 (马尔可夫链简化版)
2. 当前事件序列与常见序列的差异度
3. 模拟中简化: 维护一个"正常事件类型转移概率表"
   例如: exec→file_open 常见, file_open→net_conn 少见
4. 当前转移概率 < 阈值时产生偏离分
```

## 第五部分：阻断机制设计（重点三）

### 5.1 设计目标

> 实现三级梯度阻断，从「温和提醒」到「强制终止」，在安全性和业务连续性之间建立弹性空间。这直接对应 Observer 的「放行/警告/阻断」分级处置。

### 5.3 三级阻断详细设计

#### Tier 1：软报告 (Soft Report)

| 属性 | 说明 |
|------|------|
| **触发条件** | 风险等级 MEDIUM；或 HIGH 但仅命中 alert 规则 |
| **对Agent的影响** | **无** — 操作正常执行，Agent 无感知 |
| **系统动作** | ① 审计日志写入 (JSON + SQLite) ② 控制台输出 ⚠️ 告警 ③ 行为图谱节点标记为橙色 ④ 触发 Webhook 回调（接口预留） ⑤ 更新事件计数器 |
| **升级条件** | 同一 Agent 在 5 分钟窗口内累计 3 次软报告 → 升级为 Tier 2 |
| **设计意图** | 模拟 Observer 的「警告」等级——不确定时先记录不阻断，让安全团队有观察窗口 |

#### Tier 2：阻止访问 (Block Access)

| 属性 | 说明 |
|------|------|
| **触发条件** | 风险等级 HIGH + 命中 block 规则；或 Tier1 升级触发 |
| **对Agent的影响** | **操作被阻止，系统继续运行** — 模拟返回 -EPERM |
| **系统动作** | ① 当前事件标记为 `blocked`，下发阻断标记 ② 审计日志写入，标注阻断原因 ③ 控制台输出 🛑 阻断 ④ 行为图谱节点标记为红色 ⑤ 生成阻断原因文本（模拟反馈给Agent的"为什么被拦"） ⑥ 阻断计数器 +1 |
| **阻断实现方式（模拟）** | 在 Python 侧：不调用后续的场景事件处理器，直接将 Decision 设为 BLOCK。在 C++ 侧（扩展时）：收到 Python 的阻断指令后，对目标 pid 的后续 syscall 返回 EPERM |
| **升级条件** | 同一 Agent 被阻断 2 次后第 3 次高危触发 → 升级为 Tier 3 |
| **设计意图** | 模拟 Observer 的「阻断」等级——精准拦截，最小化业务影响 |

#### Tier 3：硬中断 (Hard Interrupt)

| 属性 | 说明 |
|------|------|
| **触发条件** | 风险等级 CRITICAL（评分 >0.9）；或 Tier2 升级触发；或检测到不可逆破坏性操作（如 `rm -rf /` 已部分执行） |
| **对Agent的影响** | **Agent 进程树被终止** — 模拟 SIGTERM → SIGKILL |
| **系统动作** | ① 发送终止信号（模拟：标记 Agent 所有进程为 terminated） ② 完整证据链紧急写入（flushing） ③ 进程树清理（标记所有子进程终止） ④ 控制台输出 💀 硬中断 ⑤ 生成完整事故报告 ⑥ 发出最高优先级告警 |
| **升后恢复** | 硬中断后 Agent 进入「隔离观察」状态，需人工手动解除才能重新启动 |
| **设计意图** | 最后防线——当温和手段已不足以阻止危险时，果断终止。对应 Observer 未明确但在真实安全系统中必需的最高等级 |

### 5.4 阻断升级机制

## 第八部分：开发实施指导（给程序员）

### 8.1 开发顺序

```
Phase 1: 数据通道 (第1-2天)
  ├─ C++ 探针层: 实现三类探针 + PipeWriter
  ├─ Python 接收端: 实现 PipeReader + RawEvent 反序列化
  └─ 联调: C++ 发送测试事件, Python 成功接收并打印

Phase 2: 监测机制 (第3-4天)
  ├─ Python: 实现 EventNormalizer (进程树 + 上下文窗口)
  ├─ Python: 实现 RuleEngine (YAML加载 + 三类规则匹配)
  ├─ Python: 编写初始规则文件 default_policy.yaml
  └─ 测试: 场景1全部事件 → 验证规则匹配正确性

Phase 3: 评判机制 (第5-7天)
  ├─ Python: 实现 RiskScorer (四维评分算法)
  ├─ Python: 实现 BaselineChecker (基线构建 + 偏离计算)
  ├─ Python: 实现 ChainReportBuilder (因果链构建 + Markdown输出)
  ├─ Python: 实现 DecisionEngine (研判矩阵)
  └─ 测试: 场景2 → 验证评分合理性 + 报告质量

Phase 4: 阻断机制 (第8-10天)
  ├─ Python: 实现 BlockingCoordinator (三级路由)
  ├─ Python: 实现 SoftReport (告警生成 + 审计写入)
  ├─ Python: 实现 BlockAccess (阻断标记 + 原因反馈)
  ├─ Python: 实现 HardInterrupt (进程终止模拟 + 证据紧急写入)
  ├─ Python: 实现 AgentViolationTracker (滑动窗口升级)
  └─ 测试: 场景2和3 → 验证阻断链条 + 升级逻辑

Phase 5: 审计与输出 (第11-12天)
  ├─ Python: 实现 BehaviorGraph (Mermaid/DOT输出)
  ├─ Python: 实现 AuditLogger (JSON + SQLite双写)
  └─ 整体联调: 三场景一键运行, 输出完整报告

Phase 6: 自优化接口 (第13天, 接口级)
  ├─ Python: 定义 ITraceStore/IPatternMiner/IStrategyGenerator

```

### 8.2 关键技术决策点

| 决策点 | 建议 | 理由 |
|--------|------|------|
| C++ 与 Python 通信方式 | Windows 命名管道 (`\\.\pipe\observer_events`) | 模拟 perf ring buffer 的单向事件流, 无需网络栈 |
| 事件序列化格式 | JSON 行协议 (每行一个事件, `\n` 分隔) | 人类可读, 调试友好, Python 原生支持 |
| Python 进程树存储 | `dict[int, ProcessNode]` + 懒删除 | 事件量小, 不需要外部数据库, 便于图谱构建 |
| YAML 规则加载 | 启动时一次性加载全部规则到内存 | 规则量小(<100条), 不需要增量更新 |
| 基线模型存储 | Python pickle 或 JSON 文件 | 模拟环境, 不需要持久化到数据库 |
| 审计日志格式 | JSON 行文件 + 可选 SQLite | JSON 便于人工查看, SQLite 预留查询能力 |

## 第十部分：一句话总结

> **C++ 层模拟 eBPF 三类探针（进程/文件/网络），通过命名管道以 JSON 行协议推送事件；Python 层实现「归一化→规则匹配→四维评分→基线偏离→链式报告→三级阻断」完整管道；自优化预留 ITraceStore/IPatternMiner/IStrategyGenerator 三个接口。总代码量预估 2500-3500 行，三场景一键运行，输出 Mermaid 图谱 + Markdown 链式风险报告，全程数据可跟踪、算法可替换、报告可阅读。**
