# 方寸观察者模拟学习系统 — 开发方案定稿

> **项目性质**：教学模拟系统 | **目标平台**：Windows 单机 | **语言**：Python（主）+ C++（探针层）| **版本**：v1.0-final

> **定稿变更摘要（相对初稿）**：新增双向命名管道（反向阻断通道）、虚拟时钟子系统、管道容错与重试机制、审计存储简化为 JSON-only、风险评分算法可替换接口、Mermaid 图谱输出简化、开发排期优化。

## 第一部分：系统总览

### 1.1 一句话定义

模拟 Fangcun Observer「OS 层无感知采集 → 风险评分 → 分级阻断 → 链式审计 → 自进化」的完整数据管道，用 C++ 模拟 eBPF 探针层、Python 实现全部业务逻辑，在单机 Windows 环境完整复现产品核心架构，产出可观察、可调试、可修改的教学级原型。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **全链路透明** | 每个处理阶段的输入/输出均可打印、可追溯，不藏黑盒 |
| **模块热插拔** | 评分算法、阻断策略、输出格式均为可替换模块（通过抽象接口实现） |
| **零外部依赖** | 标准库优先，Python 仅需 `pyyaml`，C++ 仅需标准库 + Win32 API |
| **接口即文档** | 模块间通过明确的数据结构通信，接口定义即架构文档 |
| **教学可演示** | 预设三个场景（正常/攻击/串谋），一键运行展示全流程 |
| **算法可替换** | 风险评分各维度均实现 `IRiskDimension` 接口，基础算法先行，后续可无缝替换 |

### 1.3 与产品愿景的对齐确认

| 产品核心能力（产品手册） | 本系统对应模块 | 覆盖度 |
|---|---|---|
| 无感知 Runtime 观测 | C++ 探针层 + 命名管道 + Python 归一化 | ✅ 完整模拟 |
| 实时主动阻断（毫秒级研判） | 四级评分 → 研判矩阵 → 三级梯度阻断 | ✅ 完整模拟（时间精度为虚拟时钟） |
| 全链路审计追责 | 链式因果报告 + 行为图谱 + JSON 审计日志 | ✅ 完整模拟 |
| 本地自进化防御 | ITraceStore / IPatternMiner / IStrategyGenerator 接口预留 | ⚠️ 接口级预留，不做实现 |
| 数据本地不上云 | 全部输出为本地文件（JSON/Markdown） | ✅ 天然满足 |

### 2.3 双向管道通信总览 [新增章节]

初稿架构仅有 C++→Python 的单向事件管道，但 Tier2/Tier3 阻断需要将指令传回 C++ 探针层（例如返回 EPERM、终止进程）。定稿新增反向指令管道：

| 管道 | 方向 | 管道名 | 协议 | 用途 |
|------|------|--------|------|------|
| **事件管道（正向）** | C++ → Python | `\\.\pipe\observer_events` | JSON 行，每行一个事件 | 探针上报捕获的系统调用事件 |
| **指令管道（反向）** | Python → C++ | `\\.\pipe\observer_commands` | JSON 行，每行一条指令 | Python 下发阻断/放行决策 |

**反向指令格式**：

```json
{
  "cmd_id": "cmd_001",
  "cmd_type": "block_event",
  "target_event_id": "evt_005",
  "target_pid": 12345,
  "action": "return_eperm",
  "reason": "命中规则 R001: block-dangerous-commands, 风险评分 0.82",
  "timestamp_ns": 1718092801000000000
}
```

**cmd_type 枚举**：

| cmd_type | 含义 | C++ 侧动作 |
|----------|------|-----------|
| `allow` | 放行 | 继续正常处理下一个事件 |
| `block_event` | 阻止当前事件 | 对该事件模拟返回 EPERM，不实际执行 |
| `terminate_process` | 终止进程 | 标记目标 pid 及子进程为 terminated |
| `heartbeat` | 心跳探测 | 回复 ACK，用于检测管道连通性 |

**C++ 侧轮询策略**：

```
C++ CommandReader 在每处理完一个事件后，非阻塞轮询反向管道：
1. 调用 PeekNamedPipe() 检查是否有数据
2. 有数据 → 读取 JSON 行 → 解析为 Command → 执行对应动作
3. 无数据 → 继续处理下一个事件（不阻塞）
4. 超时（500ms 无响应）→ 记录警告日志，按默认策略放行
```

**容错与异常处理**：

| 异常场景 | 处理策略 |
|---------|---------|
| 正向管道连接断开 | Python PipeReader 自动重连（最多 3 次，间隔 1s/2s/4s 指数退避） |
| 反向管道连接断开 | C++ CommandReader 降级为"全放行"模式 + 控制台告警 |
| 管道写入失败（缓冲区满） | 事件暂存本地环形缓冲区（最多 1000 条），管道恢复后补发 |
| 心跳超时（连续 3 次无 ACK） | 标记对端不可达，触发告警，按降级策略运行 |

### 3.1 设计目标

#### 3.2.1 三类探针的职责

| 探针 | 对应系统调用 | 捕获字段 | 模拟方式 |
|------|------------|---------|---------|
| **ProcessProbe** | `execve`, `fork`, `clone` | executable, arguments, env_vars | 接收场景事件规格，补充 pid/ppid/虚拟时间戳 |
| **FileProbe** | `openat`, `unlink`, `rename` | file_path, file_op, file_flags | 接收文件操作规格，补充进程上下文 |
| **NetworkProbe** | `connect`, `sendto`, DNS | remote_addr, remote_port, protocol, direction | 接收网络操作规格，补充协议信息 |

#### 3.2.2 探针关键设计决策

**决策 1：探针同步/异步？**
模拟系统中探针为同步处理（每次处理一个事件），PipeWriter 设为非阻塞。真实 eBPF 中探针是内核异步触发的，此处仅教学模拟。

**决策 2：进程上下文管理**
C++ 探针维护简易进程表（`std::unordered_map<uint32_t, ProcessInfo>`）。execve 事件自动注册新进程，后续文件/网络事件通过 pid 查询补充 agent_id 和 ppid。进程终止时标记为 terminated（懒删除，保留历史查询能力）。

**决策 3：Agent 识别**
场景事件规格携带 `agent_id`。首次 execve 建立 `agent_id → pid` 映射，子进程自动继承 agent_id。

**决策 4：管道写入失败缓冲 [新增]**
PipeWriter 内部维护环形缓冲区（`RingBuffer<1024>`），当管道写入失败（对端未连接/缓冲区满）时，事件暂存缓冲区。管道恢复后按 FIFO 顺序补发，保证事件不丢失。

### 3.3 虚拟时钟子系统 [新增章节]

#### 3.3.1 设计动机

场景事件中的 `delay_ms` 是事件间的时间间隔元数据。如果直接使用系统真实时间，运行速度受限于实际处理耗时，无法快速演示且结果不确定。因此引入虚拟时钟：

#### 3.3.2 VirtualClock 设计

```python
class VirtualClock:
    """虚拟时钟 — 按场景 delay_ms 推进，驱动全系统时间判定"""

    def __init__(self, start_ns: int = 0):
        self._current_ns = start_ns  # 虚拟时间（纳秒）

    def advance(self, delay_ms: int) -> int:
        """推进时间，返回推进后的时间戳"""
        self._current_ns += delay_ms * 1_000_000
        return self._current_ns

    def now_ns(self) -> int:
        return self._current_ns

    def elapsed_ms(self) -> int:
        """从启动到现在的虚拟经过时间（毫秒）"""
        return self._current_ns // 1_000_000

    def reset(self, start_ns: int = 0):
        self._current_ns = start_ns
```

#### 3.3.3 虚拟时钟的影响范围

| 使用虚拟时钟的模块 | 具体用途 |
|---|---|
| C++ EventFormatter | 事件 timestamp_ns 由虚拟时钟生成（Python 侧在事件注入时赋值） |
| AgentViolationTracker | 违规升级的 5 分钟滑动窗口基于虚拟时钟判定 |
| BaselineChecker | 时间模式偏离分析基于虚拟时钟 |
| EventNormalizer | 事件序列窗口超时清理基于虚拟时钟 |
| ChainReportBuilder | 因果链中步骤间时间差基于虚拟时钟 |

**注意**：C++ 探针层生成的 `timestamp_ns` 统一由 Python 侧在事件注入阶段用 VirtualClock 覆盖，保证全系统时间源一致。C++ 侧不维护独立时钟。

### 4.3 风险评分算法可替换接口 [新增]

```python
from abc import ABC, abstractmethod

class IRiskDimension(ABC):
    """风险评分维度抽象接口 — 所有评分算法必须实现此接口"""

    @abstractmethod
    def score(self, event: 'NormalizedEvent', match: 'MatchResult',
              context: 'AgentContext', baseline: 'BaselineModel') -> float:
        """计算该维度的风险分, 返回 0.0 ~ 1.0"""
        ...

    @abstractmethod
    def name(self) -> str:
        """维度名称, 用于报告输出"""
        ...

    @property
    @abstractmethod
    def weight(self) -> float:
        """该维度在综合评分中的权重"""
        ...
```

**定稿实现策略**：本次先实现基础版算法（`BasicRuleScore`, `BasicBaselineScore`, `BasicContextScore`, `BasicSequenceScore`），后续如需更复杂的算法（如基于马尔可夫链的序列异常检测），只需新增实现类并在 `config.yaml` 中切换，无需修改 RiskScorer 主体代码。

### 4.4 四维评分算法详解

#### D1：规则命中分 (RuleMatchScore) — 权重 40%

```
计算逻辑:
1. 从 MatchResult 获取命中规则列表
2. 取最高优先级: score = highest_priority / 100
3. 多条规则命中加分: score = min(score + 0.1 × (命中数-1), 1.0)

示例:
- 命中 R001(priority=100): score = 1.0
- 命中 R004(priority=50):  score = 0.5
- 同时命中 R001+R003:      score = min(1.0 + 0.1, 1.0) = 1.0
```

#### D2：基线偏离分 (BaselineDeviationScore) — 权重 25%

```
计算逻辑:
1. 四个子维度偏离值加权合成:
   time_deviation × 0.3 + path_deviation × 0.3
   + net_deviation × 0.25 + freq_deviation × 0.15
2. 每个子维度输出 0.0(正常) ~ 1.0(异常)

基线构建方式 (模拟):
- 首次运行无基线 → 场景1(正常开发)充当冷启动基线
- 场景1运行后 → 建立"正常行为"基线模型
- 场景2/3运行时 → 可检测到偏离

冷启动处理:
- 第一个场景运行时, baseline_deviation 固定返回 0.0
- 场景结束后自动保存基线快照到 output/baselines/
- 后续场景加载已有基线, 偏离检测生效
```

#### D3：上下文风险分 (ContextRiskScore) — 权重 20%

```
计算逻辑:
1. 从 EventNormalizer 获取虚拟时钟滑动窗口内最近 N 个事件 (N=10)
2. 检查可疑行为序列:
   - "读取敏感文件 + 网络外联" → +0.3
   - "多次权限提升尝试"       → +0.4
   - "跨Agent数据流动"        → +0.5
3. score = 累计加分, 上限 1.0
```

#### D4：序列异常分 (SequenceAnomalyScore) — 权重 15% [简化]

```
初稿方案: 马尔可夫链事件类型转移概率模型 → 实现复杂
定稿简化方案: 事件类型频率偏差模型

计算逻辑 (基础版):
1. 维护 Agent 的历史事件类型频率分布: freq_map[event_type] = count
2. 当前窗口内事件类型与历史频率的偏差:
   - 新出现的事件类型（历史未见过）→ +0.3/个
   - 频率异常偏高（当前窗口频率 > 历史均值 × 2）→ +0.2/个
3. score = 累计加分, 上限 1.0
4. 冷启动期（事件数 < 20）→ 固定返回 0.0

可替换性: 后续可替换为马尔可夫链版本，只需实现 IRiskDimension 接口
```

### 5.1 设计目标

### 5.2 三级阻断架构（含反向管道联动）

```

    ┌───────────┐      ┌───────────┐       ┌───────────┐

    │ SoftReport│      │BlockAccess│       │HardInterrupt│
    └───────────┘      └───────────┘       └───────────┘

    Python 侧动作:      Python 侧动作:       Python 侧动作:
    记录+告警+图谱      标记blocked+审计     标记terminated+紧急写入
```

### 5.3 三级阻断详细设计

#### Tier 1：软报告 (Soft Report)

| 属性 | 说明 |
|------|------|
| **触发条件** | 风险等级 MEDIUM；或 HIGH 但仅命中 alert 规则 |
| **对 Agent 的影响** | **无** — 操作正常执行 |
| **系统动作** | ① JSON 审计日志写入 ② 控制台 ⚠️ 告警 ③ 行为图谱橙色节点 ④ 更新事件计数器 |
| **反向管道指令** | `{"cmd_type": "allow", "target_event_id": "evt_xxx"}` |
| **升级条件** | 同一 Agent 在虚拟时钟 5 分钟窗口内累计 3 次 → 升级 Tier2 |

#### Tier 2：阻止访问 (Block Access)

| 属性 | 说明 |
|------|------|
| **触发条件** | 风险等级 HIGH + 命中 block 规则；或 Tier1 升级 |
| **对 Agent 的影响** | **操作被阻止，系统继续运行** — 模拟返回 EPERM |
| **系统动作** | ① 事件标记 `blocked` ② 审计日志写入 ③ 控制台 🛑 阻断 ④ 图谱红色节点 ⑤ 生成阻断原因文本 ⑥ 阻断计数器 +1 |
| **反向管道指令** | `{"cmd_type": "block_event", "target_event_id": "evt_xxx", "action": "return_eperm"}` |
| **升级条件** | 被阻断 2 次后第 3 次高危触发 → 升级 Tier3 |

#### Tier 3：硬中断 (Hard Interrupt)

| 属性 | 说明 |
|------|------|
| **触发条件** | 评分 >0.9；或 Tier2 升级；或不可逆破坏性操作 |
| **对 Agent 的影响** | **Agent 进程树被终止** — 模拟 SIGTERM→SIGKILL |
| **系统动作** | ① 标记 Agent 所有进程 terminated ② 证据链紧急写入 ③ 进程树清理 ④ 控制台 💀 ⑤ 完整事故报告 ⑥ 最高优先级告警 |
| **反向管道指令** | `{"cmd_type": "terminate_process", "target_pid": xxx}` |
| **恢复** | Agent 进入隔离观察状态，需人工手动解除 |

### 5.4 阻断升级机制

```
同一 Agent 的虚拟时钟滑动窗口计数器:

新事件到达, RiskAssessment.score > 阈值
        │
        ▼
查询 AgentViolationTracker
┌─────────────────────────────────────────┐
│ violation_window: 虚拟时钟过去5分钟内    │
│ tier1_count: N1                         │
│ tier2_count: N2                         │
└──────────────────┬──────────────────────┘
                   ▼
  N1 >= 3 ? ──Yes──→ 升级到 Tier2
    └No
  N2 >= 2 ? ──Yes──→ 升级到 Tier3
    └No
  执行当前 Tier

窗口过期后计数器自动清除（基于虚拟时钟）
```

### 5.5 阻断行动一览

| 操作类型 | Tier 1 | Tier 2 | Tier 3 |
|---------|:---:|:---:|:---:|
| 操作继续执行 | ✅ | ❌ (EPERM) | ❌ |
| 审计日志记录 | ✅ 标准 | ✅ 详细 | ✅ 紧急 |
| 控制台输出 | ⚠️ 黄色 | 🛑 红色 | 💀 红色+闪烁 |
| 行为图谱更新 | ✅ 橙色 | ✅ 红色 | ✅ 红色+告警 |
| Agent 通知 | ❌ | ✅ 阻断原因 | ✅ 终止原因 |
| 终止进程 | ❌ | ❌ | ✅ |
| 反向管道指令 | allow | block_event | terminate_process |
| 隔离状态 | ❌ | ❌ | ✅ 需手动解除 |

```python
class IStrategyGenerator(ABC):
    def generate(self, patterns) -> List[PolicyRule]: ...
```

### 7.3 场景执行流程

```
python main.py --scenario all

1. 加载 config.yaml（管道名、评分权重、超时参数）
2. 启动 C++ 探针进程（cpp_probe.exe）
3. 等待正向管道连接 + 反向管道连接
4. 初始化 VirtualClock
5. 依次加载场景 YAML
6. 逐条事件:
   a. VirtualClock.advance(delay_ms)

   d. Python PipeReader 接收 → 全链路处理
   e. 如需阻断 → CommandSender 写入反向管道
   f. C++ CommandReader 轮询获取指令 → 执行
7. 场景结束 → 导出报告 + 审计日志 + 图谱
8. 输出运行摘要
```

### 8.2 关键技术决策总表

| 决策点 | 定稿方案 | 理由 |
|--------|---------|------|
| C++↔Python 通信 | 双向命名管道（正向事件 + 反向指令） | 解决阻断反馈回路，架构清晰 |
| 事件序列化 | JSON 行协议 | 人类可读，调试友好 |
| 时间模型 | 虚拟时钟 (VirtualClock) | 确定性强，运行速度快，适合教学 |
| 审计存储 | 仅 JSON 行文件 | 教学原型足够，降低开发量 |
| 风险算法 | IRiskDimension 可替换接口 + 基础实现 | 先跑通，后续可拓展 |
| 图谱输出 | 结构化 JSON 为主，Mermaid 简化 | 保障严谨溯源，降低开发复杂度 |
| 报告输出 | Markdown 风险分析报告 + 结构化 JSON | 用户可读 + 程序可解析 |
| 进程树存储 | `dict[int, ProcessNode]` + 懒删除 | 事件量小，无需外部数据库 |
| 规则加载 | 启动时全量加载到内存 | 规则量小 (<100 条) |
| 基线存储 | JSON 文件 (output/baselines/) | 模拟环境，不需要数据库 |
| 管道容错 | RingBuffer 暂存 + 指数退避重连 | 保证事件不丢失 |

### 8.5 边界条件与异常处理策略 [新增]

| 边界条件 | 处理策略 |
|---------|---------|
| 管道满（写入阻塞） | PipeWriter RingBuffer 暂存，恢复后补发 |
| 冷启动无基线 | 第一个场景偏离分固定 0.0，场景结束后自动保存基线 |
| 多 Agent 并发事件 | 按 event_id 顺序串行处理（教学原型不需要并发） |
| 规则文件缺失/格式错误 | RuleEngine 启动时校验，错误规则跳过并告警，不中断运行 |
| 场景 YAML 格式错误 | ScenarioLoader 校验失败时打印错误位置，退出并提示 |
| 虚拟时钟溢出 | 使用 Python int（任意精度），不存在溢出问题 |
| Agent 已 terminated 后收到事件 | EventNormalizer 丢弃该事件并记录警告 |
| 反向管道超时（C++ 500ms 无响应） | 降级为默认放行 + 控制台告警 |

## 总结

> **C++ 层模拟 eBPF 三类探针（进程/文件/网络），通过双向命名管道（正向事件 + 反向指令）以 JSON 行协议通信；Python 层实现「归一化→规则匹配→四维可替换评分→基线偏离→链式报告→三级梯度阻断」完整管道，虚拟时钟驱动全系统时间判定；审计日志仅 JSON 行文件；自优化预留三个接口。总代码量预估 2500-3500 行，三场景一键运行，输出 Markdown 风险分析报告 + 结构化 JSON 溯源数据，全程数据可跟踪、算法可替换、报告可阅读。**
