## 一、核心引擎测试

### 1.1 test_virtual_clock.py（16 个测试）

- **设计目的**：验证虚拟时钟的精度、推进和重置行为。虚拟时钟是模拟模式的时间基础，所有场景事件的时间戳由它产生。
- **期望结果**：时钟按 `delay_ms` 步进推进；`now_ns()`/`now_ms()` 返回值单调递增；重置后时间归零；毫秒截断精度正确。
- **功能点**：
  - 虚拟时钟的纳秒精度
  - 时间推进的可控性
  - 时钟重置的幂等性
  - 跨场景时间隔离

### 1.2 test_pipe_communication.py（26 个测试）

- **设计目的**：验证双向管道通信的可靠性，包括正向管道（探针→引擎）和反向管道（引擎→探针）的数据传输。
- **期望结果**：JSON 事件序列化/反序列化不丢数据；心跳机制正常运作；管道断开后检测到异常；大数据量传输不溢出缓冲区。
- **功能点**：
  - 事件 JSON 序列化与反序列化
  - 心跳检测与超时处理
  - 管道连接的建立与断开
  - RingBuffer 缓冲与补发机制
  - 反向管道的指令发送与确认

### 1.3 test_monitoring.py（18 个测试）

- **设计目的**：验证事件归一化处理和规则引擎匹配逻辑。这是系统的"眼睛"——将原始事件转化为可分析的归一化事件，并用规则进行初步筛选。
- **期望结果**：RawEvent 正确转为 NormalizedEvent；命令字符串正确拼接（executable + arguments）；规则引擎按策略文件匹配 exec/file_open/net_conn 三类事件。
- **功能点**：
  - 事件归一化（RawEvent → NormalizedEvent）
  - 命令字符串拼接（用于规则匹配）
  - 规则引擎的子串匹配和正则匹配
  - 进程树节点关联
  - 滑动窗口事件管理

### 1.4 test_judgment.py（21 个测试）

- **设计目的**：验证四维风险评分和三级决策判定。这是系统的"大脑"——综合多个维度计算风险分数，做出 ALLOW/ALERT/BLOCK 决策。
- **期望结果**：四维评分（规则匹配/基线偏离/上下文风险/序列异常）按权重合成；风险等级正确划分（LOW/MEDIUM/HIGH/CRITICAL）；决策引擎输出 ALLOW/ALERT/BLOCK。
- **功能点**：
  - 四维风险评分模型
  - 权重配置（0.40/0.25/0.20/0.15）
  - 风险等级阈值划分
  - 三级决策判定逻辑
  - 链式报告构建

### 1.5 test_blocking.py（16 个测试）

- **设计目的**：验证三级梯度阻断机制和违规升级逻辑。这是系统的"手"——根据决策结果执行阻断操作。
- **期望结果**：Tier1 警告 → Tier2 阻断单次操作 → Tier3 终止进程；违规次数在滑动窗口内累积；窗口过期后违规计数清零。
- **功能点**：
  - 三级梯度阻断（TIER1/TIER2/TIER3）
  - 违规追踪器的滑动窗口
  - 阻断升级阈值（Tier1→Tier2→Tier3）
  - 阻断命令的发送与确认
  - 隔离状态管理

### 1.6 test_audit.py（16 个测试）

- **设计目的**：验证审计日志记录和报告导出功能。这是系统的"记忆"——所有决策和操作都有据可查。
- **期望结果**：审计日志按 JSONL 格式写入；行为图谱正确记录事件节点和边；报告导出包含完整的风险评分和决策信息。
- **功能点**：
  - 审计日志的 JSONL 格式输出
  - 行为图谱的节点/边记录
  - 风险分析报告的生成与导出
  - 输出目录管理

### 1.7 test_integration.py（17 个测试）

- **设计目的**：验证核心引擎的端到端完整流程——从事件输入到审计输出。确保各模块协作正确。
- **期望结果**：完整的"事件→归一化→评分→判定→阻断→审计"链路无断裂；37 个场景全部通过。
- **功能点**：
  - 端到端流程完整性
  - 模块间数据传递正确性
  - 场景驱动的完整运行
  - 多场景批量处理

## 二、适配层测试

### 2.1 test_adapter.py（23 个测试）

- **设计目的**：验证平台检测逻辑和 Collector 工厂函数。这是系统的"调度员"——根据运行环境自动选择最合适的采集器。
- **期望结果**：正确检测 Windows/Linux 平台；eBPF 能力检查（BTF/libbpf/CAP_BPF）准确；工厂函数根据 mode 参数创建正确的 Collector 实例；auto 模式降级链路（eBPF→strace→simulation）正确。
- **功能点**：
  - 平台检测（Windows/Linux）
  - eBPF 能力探测
  - Collector 工厂函数（4 种模式路由）
  - 降级链路逻辑
  - PlatformInfo 数据完整性

## 三、采集层测试

### 3.1 test_simulation_collector.py（28 个测试）

- **设计目的**：验证模拟采集器——从 YAML 场景文件加载事件并逐条 yield RawEvent。这是教学演示和开发调试的主要模式。
- **期望结果**：正确加载 37 个 YAML 场景文件；事件按 delay_ms 间隔 yield；capabilities 声明阻断能力（can_block_tier2/3=True）；send_command 正确发送阻断指令。
- **功能点**：
  - YAML 场景文件加载与解析
  - 虚拟时钟驱动的事件生成
  - 阻断能力声明
  - 生命周期管理（attach/start/detach）
  - 进程树模拟

### 3.2 test_ebpf_collector.py（30 个测试）

- **设计目的**：验证 eBPF 采集器——通过 mock libbpf 测试事件结构体解析和 RawEvent 转换。无需真实 eBPF 环境。
- **期望结果**：EventT ctypes 结构体正确定义；perf ring buffer 回调正确处理事件数据；三种事件类型（execve/openat/connect）的字段映射正确；detach 清理所有 eBPF 资源。
- **功能点**：
  - EventT 结构体与 eBPF C 代码的一致性
  - libbpf ctypes 绑定
  - perf ring buffer 事件消费
  - argv 解析（memmove 读取完整缓冲区）
  - 资源清理与 atexit 注册

### 3.3 test_strace_collector.py（45 个测试）

- **设计目的**：验证 strace 采集器——从 strace 子进程输出逐行解析 execve/openat/connect 系统调用。这是 eBPF 不可用时的降级方案。
- **期望结果**：三个正则表达式正确匹配 strace 输出格式；subprocess.Popen 管理 strace 进程；线程安全行队列正常运作；detach 时 terminate+kill 清理子进程。
- **功能点**：
  - strace 行解析正则（execve/openat/connect）
  - subprocess 进程管理
  - 线程安全的行队列
  - 超时强制终止（terminate→kill）
  - capabilities 声明（不支持阻断）

### 3.4 test_file_replay_collector.py（39 个测试）

- **设计目的**：验证文件回放采集器——从外部 JSONL/CSV 文件导入测试数据。这是外部测试信息接入的核心接口。
- **期望结果**：JSONL 文件逐行解析正确（支持注释行和空行）；CSV 文件正确解析（处理空字段和类型转换）；数据校验规则生效（缺少 event_type 跳过、未知类型跳过）；白盒测试数据文件（malicious_curl/normal_dev/sample_events）回放正确。
- **功能点**：
  - JSONL 格式加载（含注释行支持）
  - CSV 格式加载（含类型自动转换）
  - 数据校验规则
  - 白盒测试数据回放
  - 与 observer_core/ 处理链路的事件格式兼容性

### 3.5 test_collector_integration.py（41 个测试）

- **设计目的**：验证四种采集模式的工厂函数切换、能力对比、事件格式一致性和降级逻辑。确保所有采集器在统一接口下行为一致。
- **期望结果**：工厂函数正确路由 simulation/ebpf/strace/file_replay 四种模式；四种采集器的 capabilities 返回值符合预期；send_command 行为一致（Simulation=True，其余=False）；三种事件类型（exec/file_open/net_conn）的 RawEvent 字段格式完全一致。
- **功能点**：
  - 工厂函数模式切换（4 种模式）
  - 采集器能力对比验证
  - send_command 跨采集器行为一致性
  - RawEvent 事件格式一致性
  - ICollector 接口一致性
  - 降级链路验证
  - PlatformInfo 平台检测

## 四、eBPF 探针验证测试

### 4.1 test_ebpf_field_mapping.py（14 个测试）

- **设计目的**：验证 EbpfCollector 的 `_to_raw_event()` 方法——将 eBPF 内核产出的 EventT 结构体正确映射为 RawEvent。确保 eBPF 模式与模拟模式在 observer_core/ 看来完全等价。
- **期望结果**：execve→exec 映射正确（filename→executable，argv→arguments）；openat→file_open 映射正确（flags→file_op：O_RDONLY→read，O_WRONLY/O_RDWR→write）；connect→net_conn 映射正确（IP 网络字节序→点分十进制，端口网络字节序→主机字节序）；时间戳原样传递，event_id 递增。
- **功能点**：
  - 三类事件的字段映射完整性
  - IP 地址和端口的字节序转换
  - argv 的 \0 分隔解析
  - 文件操作标志位映射
  - 未知事件类型的安全处理

### 4.2 test_ebpf_edge_cases.py（13 个测试，1 skipped）

- **设计目的**：验证模拟探针无法覆盖的边缘情况——长路径截断、高频事件冲击、失败 syscall 处理和 agent_id 一致性。
- **期望结果**：超长路径（>256 字节）截断后不崩溃；1000 个高频事件正常处理不丢不卡；失败的 syscall 事件正常转换（eBPF 在入口触发，不区分成功失败）；同一 Agent 的所有事件 agent_id 相同。
- **功能点**：
  - 长路径截断安全处理
  - 高频事件吞吐能力
  - 失败 syscall 的事件转换
  - agent_id 跨事件/跨 PID 一致性
  - detach 后资源清理

### 4.3 test_ebpf_performance.py（4 个测试）

- **设计目的**：建立 eBPF 事件处理的性能基线，验证 eBPF 与模拟模式的事件格式等价性。
- **期望结果**：单事件处理延迟 <1ms；100 个事件批量处理 <100ms；eBPF 的 event_type 值域与模拟模式完全一致；RawEvent 包含 observer_core/ 所需的全部字段。
- **功能点**：
  - 事件处理延迟基线
  - 批量处理吞吐
  - event_type 值域等价性
  - RawEvent 字段兼容性

## 五、辅助工具

### 5.1 tools/test_agent.py

- **设计目的**：产生真实 syscall 供 eBPF 探针捕获，用于验证 EbpfCollector 在真实环境下的采集能力。
- **使用方式**：`python3 tools/test_agent.py --scenario <场景名>`
- **支持场景**：

| 场景 | 操作 | 覆盖 syscall |
|------|------|:---:|
| baseline_check | ls → cat → curl | execve, openat, connect |
| long_path | 创建 300 字节文件名 → 读写 | openat |
| flood | 循环 100 次 /bin/true | execve |
| fork_chain | bash -c 'ls && cat && whoami' | execve（含父子进程） |
| failed_ops | cat /etc/shadow + 不存在命令 | execve/openat（失败） |
| network | curl + socket 连接 | connect |
