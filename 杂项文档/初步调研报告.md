# Fangcun Observer 初步调研总体概述

一句话概述：Fangcun Observer是通过对AGENT运行时OS/Runtime数据的监测，而不是与AGENT进行交互，评判系统运行的安全状态，得出链式结构化安全风险报告，在发生严重安全威胁时能在危险指令生效前阻断系统运行，并且它还有自优化功能，通过自身记录的历史数据，对其监测的系统进行针对性优化，实现在数据库不上传的情况下自优化。

# 关键模块专业名词解析

## AI Agent Runtime

### Runtime 具体在做什么？

内存管理：
栈（Stack）：自动分配局部变量，函数返回时自动回收。
堆（Heap）：Runtime 负责动态分配内存（如 new 或 malloc），并通常包含 垃圾回收器（GC） 来自动清理不再使用的对象。
类型检查：
有些语言（如 Java, Python）在 Runtime 检查类型（动态类型/强类型）；有些语言（如 C++, Rust）尽量在 Compile-time 完成，以减少 Runtime 开销。
异常处理：
当发生错误时，Runtime 负责捕获异常、展开调用栈（Stack Unwinding）并执行 catch 块。
I/O 与系统调用：
Runtime 封装了操作系统的 API。比如你写 print("Hello")，Runtime 会将其转换为操作系统的 write 系统调用。
并发与调度：
管理线程、协程（Goroutine/Fiber）的创建、切换和同步。
### AI Agent Runtime（AI 智能体运行时） 
是专为运行和管理 AI Agent 而设计的执行环境和基础设施平台。如果说传统的 Runtime 是普通程序的“后勤系统”，那么 AI Agent Runtime 则是赋予 AI 智能体“自主行动能力”的操作系统逻辑与中枢神经。
普通的 AI 模型（如基础大语言模型）通常只是无状态的，只能针对单个提示词返回一段文本；而 AI Agent Runtime 则充当了将静态模型与真实世界连接起来的“活跃组织”，让 AI 能够进行多步推理、调用工具并自主完成复杂任务。
AI Agent Runtime 的核心架构与能力主要体现在以下几个维度：
1. 核心推理与编排机制
Agent Runtime 内部通常包含一个事件循环（Event Loop）和编排引擎（Orchestration Engine）。它负责协调模型调用、管理工具，并解析模型返回的思考与行动指令，将其转化为下一步的实际操作。这种持续的控制结构让单次查询变成了连贯的问题解决过程，并确保 AI 在执行长任务时不会偏离轨道。
2. 状态与生命周期管理
与传统的无状态推理不同，AI Agent 需要维持复杂的上下文。Runtime 提供了完善的状态管理（State Management）和会话隔离（Session Isolation）机制：
会话隔离：每个用户的对话通常会被分配独立的执行环境（如专用的 microVM），拥有隔离的计算、内存和文件系统资源，防止不同用户之间的数据污染或凭证泄露。
持久化与恢复：通过持久执行（Durable Execution）和状态检查点机制，Runtime 会在执行过程中自动保存进度。如果底层硬件发生故障，系统可以从特定断点无缝恢复，而不需要从头重新计算。
3. 企业级安全与凭证管理
当 AI Agent 需要代替人类执行特权操作（如访问数据库、调用第三方 API）时，安全性至关重要。Agent Runtime 提供了严格的身份与凭证管理机制：
它通过抽象层集中管理密码、API Key 等敏感信息，在运行时动态注入，避免敏感数据直接暴露给大模型。
支持入站和出站的身份验证（如 OAuth 2.0），确保 Agent 只能在被授权的范围内代表用户或自主执行任务。
4. 全链路可观测性（Observability）
在生产环境中，AI Agent 不能是一个“黑盒”。Agent Runtime 提供端到端的链路追踪能力，记录从用户请求、网关、Agent 推理、模型调用到工具执行的每一个环节。这不仅有助于性能监控和成本归因（如精确统计 Token 消耗），还能在出现异常时进行故障诊断、安全审计和质量评估。
5. 极致弹性与安全沙箱
为了应对不可预测的 AI 行为或突发流量，现代 Agent Runtime 通常采用 Serverless（无服务器）架构：
安全沙箱：为代码执行或浏览器操作提供毫秒级启动、VM 级别的安全隔离环境，确保即使 AI 执行了恶意代码也不会影响宿主系统。
弹性伸缩：支持根据请求量自动扩缩容，甚至在低峰期缩容到 0，以优化计算成本。

## OS/Runtime 层
1. OS 层的核心职责：全局资源与硬件抽象
操作系统是计算机的“总控中心”，它向上层屏蔽了物理硬件的复杂性：
硬件抽象：程序不需要知道硬盘是机械盘还是固态盘，也不需要知道网卡的具体型号。OS 通过驱动程序和统一的系统调用（System Calls，如 read, write, socket）提供标准化的接口。
进程与线程调度：OS 决定哪个程序在什么时候使用 CPU，实现多任务并发。它通过时间片轮转、优先级等算法，让多个程序看起来像是在“同时”运行。
内存虚拟化：OS 为每个进程提供独立的虚拟内存空间，通过 MMU（内存管理单元）将虚拟地址映射到物理内存，防止程序 A 意外覆盖程序 B 的数据。
文件系统与 I/O 管理：将物理存储抽象为目录和文件，并提供缓存机制以加速读写。
2. Runtime 层的核心职责：语言特性与开发便利
Runtime 是特定语言或框架的“贴身管家”，它运行在 OS 之上，为程序提供更高级别的便利：
内存管理：如 Java 的 GC（垃圾回收）、Go 的 GC、Rust 的所有权检查。它们自动处理内存的分配与释放，减轻开发者负担。
并发模型：如 Java 的线程池、Go 的 Goroutine、Node.js 的事件循环。Runtime 将 OS 沉重的线程/进程调度，映射为轻量级的语言级并发原语。
标准库与 API：提供跨平台的网络请求、JSON 解析、正则表达式等高级功能，无需开发者直接调用底层的 OS API。
类型系统与异常处理：在运行时进行动态类型检查、反射、异常捕获与栈展开。
3. OS 与 Runtime 的协作关系
它们不是孤立的，而是紧密配合的：
Runtime 依赖 OS：当 Java 程序需要分配内存时，JVM 最终会调用 OS 的 mmap 或 brk 系统调用；当 Node.js 需要读取文件时，libuv 会调用 OS 的 open 和 read。
OS 依赖 Runtime（在某些场景）：现代 OS 的许多组件本身就是用高级语言编写的（如 Windows 的很多服务用 C#，macOS 的 Finder 用 Swift），这些组件依赖各自的 Runtime 运行。
4. 为什么这一层如此重要？
安全性：通过权限隔离、内存保护，防止恶意程序破坏系统或窃取数据。
可移植性：开发者只需针对 OS/Runtime 编程，无需关心底层是 x86 还是 ARM，是 Linux 还是 Windows。
效率：通过缓存、调度、并发复用等机制，最大化硬件利用率。
开发效率：将复杂的底层逻辑封装为简单的 API，让开发者专注于业务逻辑。

## Harness、模型供应商

### Harness
Harness（智能体控制底座 / 编排框架）
在 AI Agent 领域，Harness 并不是指简单的代码框架（如 LangChain），而是指多智能体执行框架（Multi-Agent Harness）。它是 Agent 的“操作系统”和“运行控制面板”，负责处理大模型推理之外的所有结构化事务，确保 AI 行为受控、安全且可观测。
### 模型供应商
模型供应商是 AI Agent 的“大脑”提供方。它们提供底层的大语言模型（LLM），负责处理自然语言理解、逻辑推理、代码生成和工具调用（Function Calling）。在 Agent 架构中，Harness 会根据任务需求，通过统一的 API 接口（如 LiteLLM 或 MCP 协议）向模型供应商发起请求。

## 二、五大核心能力深度拆解

产品手册和公开资料一致指向五项核心能力，形成「看见→研判→阻断→追溯→进化」的完整闭环：

| 能力 | 核心描述 | 关键技术特征 |
|---|---|---|
| **① 无障碍接入** | 开箱即用，彻底解耦 Harness | OS 层直接观测，不依赖任何框架插件/SDK/模型供应商集成 |
| **② 无感知 Runtime 观测** | 业务代码 0 修改，Agent 无感知 | 覆盖系统命令执行、文件读写、网络连接三大 side effect 维度 |
| **③ 实时主动阻断** | 毫秒级研判，防患于未然 | 风险评分→策略研判→内核阻断，支持放行/警告/阻断三级分级处置 |
| **④ 全链路审计追责** | 完整行为图谱，不可抵赖证据链 | Runtime side effect + Agent 决策 + LLM context 关联为统一图谱 |
| **⑤ 本地自进化防御** | 数据不上云，越用越安全 | Trace 沉淀→数据挖掘→策略生成→上线验证，形成组织专属行为基线 |

### 2.1 无感知采集逻辑（技术原理）

Observer 的核心观测机制工作在 **OS 层**，不与 Agent 应用发生任何交互。它捕获的是 Agent 的 **side effect**——即 Agent 在操作系统层面产生的真实副作用（系统调用、文件操作、网络请求），而非 Agent 框架自报的日志或 SDK 上报的数据 [3]。

关键设计原则：
- **0 业务代码修改**：不需要在 Agent 代码中插入任何 hook、SDK 或探针
- **跨所有 Agent 框架**：无论底层使用 LangChain、Dify、Coze、AutoGen、CrewAI 还是自定义框架，因工作在 OS 层故通用有效
- **Agent 无感知**：Agent 无法检测到自己正在被观测，消除「表演」行为空间——这也是产品手册反复强调的："Agent 不会知道自己正在被观测——你看到的，是它真正的行为。不是它「表演」给你看的样子。" [3][4]

### 2.2 可监控行为范围

产品手册明确列出三大类监控对象：
- **系统命令执行**：编译运行、脚本执行、进程创建等
- **文件读写**：敏感文件读取、代码文件写入、删除、压缩等
- **网络连接**：外联域名、DNS 解析、数据外传、API 调用等

### 2.3 实时阻断流程

```
Agent 发起操作 → OS 层捕获 side effect → 风险评分（实时） → 策略研判（毫秒级）
                                                                  ├── 放行：低风险，正常执行
                                                                  ├── 警告：中风险，通知但允许
                                                                  └── 阻断：高风险，内核级拦截（在 side effect 落地前）
```

阻断发生在 **side effect 真正落地之前**，这是区别于传统「事后审计」的关键差异 [3]。

### 2.4 审计链路

将 Runtime side effect、Agent 决策动作与 LLM context 关联为**完整的行为图谱**，支持：
- 单 Agent 和多 Agent 协作链路的全链路追溯
- 时间线还原完整决策路径
- 风险定位直达源头
- 不可抵赖的行为证据链

### 2.5 自进化闭环

```
Trace 沉淀 → 数据挖掘 → 策略生成 → 验证部署 → (循环回 Trace 沉淀)
```

所有数据**纯本地存储，不上云、不外传**。策略模型基于组织真实运行数据持续迭代，从静态规则演进为具备自学习能力的防御体系 [1]。

## 四、差异化卖点与竞争分析

### 4.1 三大核心差异化

| 差异化维度 | Fangcun Observer | 传统方案（Prompt 防火墙/框架插件/SDK 上报） |
|---|---|---|
| **数据本地不上云** | 所有观测、审计、事件数据纯本地沉淀 | 日志/数据常需上传云端或依赖第三方服务 |
| **内核级感知** | OS 层捕获真实 side effect，不可伪造 | 依赖 Agent 自报日志或 SDK 上报，存在篡改/伪装空间 |
| **消除伪装欺骗空间** | Agent 无法感知观测，消除 sandbagging 与主动 deception | Agent 可通过修改日志/SDK 输出隐藏真实行为 |

### 4.2 核心竞品对比：eunomia AgentSight + ActPlane

在 OS 层 Agent 运行时安全领域，最直接的竞品是 **eunomia-bpf 开源团队**的 AgentSight（观测）和 ActPlane（执行控制） [1][2]。

| 对比维度 | Fangcun Observer | eunomia AgentSight + ActPlane |
|---|---|---|
| **产品形态** | 一体化企业平台（观测+阻断+审计+进化合一） | 开源双工具——观测与执行控制分离 |
| **技术路线** | 未公开具体实现（推测 eBPF 或内核模块） | 明确基于 eBPF，开源透明 |
| **观测能力** | 系统命令、文件读写、网络连接 | 进程谱系 + TLS/网络 + LLM API 调用 + 工具调用 + 文件访问 |
| **阻断能力** | 内核级阻断 + 分级处置（放行/警告/阻断） | ActPlane YAML 策略编译为 eBPF，支持标签传播、因果排序、过期失效 |
| **审计溯源** | 行为图谱 + LLM context 关联 | 进程树 + 时间线，可回放 |
| **自进化** | ✅ 核心卖点——Trace 沉淀→策略生成闭环 | ❌ 未声称此能力 |
| **商业模式** | 企业级商业产品 | 开源社区驱动 + 企业服务 |
| **性能开销** | 声称"计算开销忽略不计" | 明确约 3% 开销 |
| **部署形态** | 本地部署，数据不上云 | 本地自托管 |

关键差异总结：Fangcun Observer 强调**一体化平台体验** + **自进化闭环** + **本地数据安全**，定位为商业企业级产品；eunomia 则走开源技术路线，强调透明性和可组合性，观测和控制拆分为两个独立工具 [1][2]。

| 安全层 | 代表产品 | Fangcun Observer 的位置 |

| 审计合规 | Smart Tokens | Observer 内置审计能力 |
| Skill 安全扫描 | Fangcun SkillWard | Fangcun 同门产品 SkillWard |

Observer 处于 OS 层行为观测与阻断这一**新出现的独立层级**，同时向下兼容审计合规需求，与同门的 Guard（内容护栏）和 SkillWard（事前扫描）形成三产品闭环 [3][4]。

## 五、初步评估与待深入问题

### 5.1 产品优势总结

1. **架构优势**：OS 层观测从根本上解决了 Agent 可伪装、日志可篡改的信任问题——这是任何应用层方案无法替代的「ground truth」来源
2. **体验优势**：零代码改动 + Agent 双无感知，降低企业接入门槛
3. **数据安全**：纯本地部署、数据不上云，切中国内政企客户核心关切
4. **闭环设计**：观测→阻断→审计→进化形成飞轮，产品越用越强，非一次性工具
5. **学术基因**：清华团队背景提供技术可信度背书

### 5.2 待深入验证的问题

1. **技术实现**：产品手册未公开具体技术路线（eBPF？内核模块？auditd？），需要技术验证
2. **性能开销量化**：手册称"计算开销忽略不计"，但无具体 benchmark 数据，与 eunomia 的 3% 无法直接对比
3. **阻断延迟**：声称"毫秒级研判"，但无 P50/P99 延迟数据
4. **跨平台支持**：是否支持 Windows/macOS，还是仅 Linux？手册未明确
5. **与 Fangcun Guard 的协同**：Observer 和 Guard 的联动机制、联合部署方案需进一步了解
6. **开源 vs 闭源生态**：eunomia 开源路线对开发者社区有天然吸引力，Fangcun 纯商业路线的生态建设策略需关注

## 二、输入流：Observer 接收什么

### 2.1 核心数据输入 —— OS 层 Side Effect（被动采集，持续实时）

这是 Observer 最根本的数据来源。Observer 工作在操作系统层，直接捕获 Agent 进程在 OS 上产生的**真实副作用**，无需 Agent 框架上报、无需 SDK 埋点。

| 数据类别 | 具体捕获内容 | 来源说明 |
|----------|-------------|----------|
| **系统命令执行** | `execve`、`fork`、`clone` 等系统调用；shell 命令、脚本执行、编译构建、进程创建与终止 | Agent 调用的任何子进程、命令行工具 |
| **文件读写** | `open`、`read`、`write`、`unlink`、`rename`、`chmod` 等文件系统调用；文件创建/修改/删除/压缩/权限变更 | Agent 对本地文件系统的所有操作 |
| **网络连接** | `connect`、`send`、`recv`、DNS 解析请求；目标 IP、域名、端口、协议、传输方向与数据量 | Agent 发起的对外网络请求 |

**关键性质**：
- 零业务代码修改，不侵入 Agent 框架
- Agent 无感知（无法意识到自己被观测），消除「表演行为」
- 跨所有 Agent Harness（LangChain / Dify / Coze / AutoGen / 自研框架通用）

### 2.2 配置数据输入 —— 安全策略与管理规则（主动配置）

| 配置项 | 内容 | 用途 |
|--------|------|------|
| **风险策略规则** | 风险阈值定义、高危操作黑名单（如 `rm -rf /`、`curl | bash` 等）、网络外联白名单 | 驱动实时风险评分与阻断决策 |
| **分级处置策略** | 什么条件放行、什么条件警告、什么条件阻断 | 定义研判引擎的分级行为 |
| **组织行为基线**（可选初始导入） | 正常业务的 Agent 行为模式、允许的进程树、合法的网络出口 | 作为异常检测的参照基准 |
| **集成对接配置** | SIEM / 告警系统 / 日志平台的接入参数 | 让输出结果进入企业现有安全运营体系 |

### 2.3 自进化循环输入 —— 历史 Trace 与基线反馈

| 数据 | 内容 | 用途 |
|------|------|------|
| **历史 Trace 沉淀** | 过往所有 Agent 行为的完整记录 | 数据挖掘的原料 |
| **人工标注/反馈** | 安全团队对误报/漏报的打标修正 | 优化策略准确率 |
| **组织业务变更信号** | 新增合法 Agent 流程、业务扩展 | 驱动基线自适应更新 |

## 三、核心处理链路

Observer 内部的处理管道，可以理解为四阶段流水线：

```
OS 层 side effect 信号
        │
        ▼
┌──────────────────┐
│ ① 行为归一化     │  原始系统调用 → 结构化行为事件
│   + 上下文关联    │  关联 Agent 进程、LLM context
└──────┬───────────┘
       │
       ▼
┌──────────────────┐
│ ② 风险评分引擎   │  实时计算风险分值
│   （毫秒级）     │  匹配已知恶意模式 + 偏离基线程度
└──────┬───────────┘
       │
       ▼
┌──────────────────┐
│ ③ 策略研判       │  根据风险评分 + 策略规则
│   （分级决策）    │  → 放行 / 警告 / 阻断
└──────┬───────────┘
       │
       ▼
┌──────────────────┐
│ ④ 图谱关联+沉淀  │  行为事件 → 写入行为图谱
│                   │  Trace 持久化，供审计+进化
└──────────────────┘
```

## 四、输出流：Observer 产出什么

### 4.1 实时输出 —— 阻断决策与动作

这是 Observer 最核心的在线产出，直接作用于 Agent 运行：

| 产出物 | 形式 | 说明 |
|--------|------|------|
| **放行决策** | 无干预，正常执行 | 低风险操作，静默通过 |
| **警告通知** | 实时告警推送（可对接 SIEM/钉钉/飞书/邮件） | 中风险操作，不阻断但通知安全团队关注 |
| **阻断动作** | 内核级拦截，操作在 side effect 落地前被终止 | 高危操作被实时阻止（如 `rm -rf`、外传敏感文件），同时生成阻断事件记录 |
| **阻断原因** | 结构化风险报告（风险类型、评分、匹配规则、触发进程） | 说明「为什么阻断」，供运维和安全团队复核 |

### 4.2 准实时/事后输出 —— 行为可视化与审计

| 产出物 | 形式 | 使用场景 |
|--------|------|----------|
| **Agent 行为图谱** | 可视化有向图，展示 Agent→进程→文件→网络的完整链路 | 安全运维人员定位问题、理解 Agent 真实行为 |
| **操作时间线** | 按时间排序的全量行为事件流，可下钻到单次系统调用 | 事件回溯、根因分析 |
| **多 Agent 协作链路图** | 跨 Agent 的交互关系、数据流向、权限传递 | 多智能体场景下的串谋检测、越权溯源 |
| **风险定位** | 在图谱/时间线上高亮标注的高风险节点 | 快速定位问题源头 |

### 4.3 合规审计输出

| 产出物 | 形式 | 使用场景 |
|--------|------|----------|
| **完整行为证据链** | Runtime side effect + Agent 决策 + LLM context 三者关联的结构化记录 | 内部审计、监管检查、第三方安全评估 |
| **合规审计报告** | 可按时间范围/Agent/风险等级导出的标准化报告 | 满足合规要求，降低审计人力成本 |
| **不可抵赖日志** | 带时间戳、进程指纹的原始行为记录，本地持久化存储 | 作为法律/合规证据 |

### 4.4 自进化产出

| 产出物 | 形式 | 说明 |
|--------|------|------|
| **新安全策略规则** | 从历史 Trace 中自动挖掘生成的检测/阻断规则 | 自动覆盖新发现的攻击模式 |
| **更新后的行为基线** | 随业务变化动态调整的正常行为模型 | 降低误报率，适应业务演进 |
| **组织安全知识资产** | 沉淀为组织专属的 Agent 安全策略库 | 安全能力随业务一同成长，不依赖外部威胁情报 |

## 六、一句话总结

> **输入**：OS 层实时捕获的 Agent 系统调用（命令执行、文件操作、网络连接） + 安全策略配置 + 历史 Trace 反馈。
>
> **产出**：实时阻断决策（放行/警告/阻断）+ 完整行为图谱与审计证据链 + 自进化的安全策略与组织行为基线。全程数据不上云、纯本地闭环。
