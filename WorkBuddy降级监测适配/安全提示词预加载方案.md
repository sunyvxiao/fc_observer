# WorkBuddy 安全提示词预加载方案

> 版本: 1.1 ｜ 适用对象: 方寸观察者（observer_sim）MCP 申报降级监测 + WorkBuddy（黑盒 Agent）
> 文档定位: 独立设计方案文档，不依赖任何项目内部模块，可单独阅读执行
> 配套文档（同目录）: `安全提示词内容.md`（可直接复制的提示词全文）、`用户使用说明.md`（操作指引）、`WorkBuddy降级监测端到端测试用例.md`（验证载体）

---

## 1. 背景与结论摘要

方寸观察者对 WorkBuddy 的降级监测依赖 **MCP 申报通道**：WorkBuddy 每次工具调用时主动调用 observer MCP 工具的 `report_tool_call` 等接口申报，观察者据此构造事件并进入判定管线。申报是 **Agent 的主动行为**——不申报即监测盲区。

本方案借鉴 ShellWard 组件 `安全提示词.txt` 的做法（在会话开始时以提示词形式向黑盒 Agent 注入"安全协作契约"），为 WorkBuddy 设计一份安全提示词，用于：

- **事前**约束 Agent 行为、明确申报义务；
- 与 **MCP 申报监测**（事后合规留痕与风险判定）形成互补，共同构成降级监测下的双环安全阀外环。

**结论**：必要且可行（附条件）。提示词由用户手动粘贴（当前即用），可选 `mcp.json instructions` 注入（实验性）。方案有效性通过 E2E 用例 **F02** 量化验证。

> **v1.1 实证补充（2026-08-25 真实 WorkBuddy 会话验证）**：
> 1. 提示词原文（v1.0）被 WorkBuddy 判定为**提示注入**而拒绝配合——「降级安全监测环境」强制框架定位与「观察者判定作为权威」「BLOCK 不真实阻断」表述触发了 Agent 内置注入防御。此为「Agent 侧安全拦截」，不计入本项目能力缺口。
> 2. 将提示词改写为**合规审计留痕**定位（v2.0，见《安全提示词内容.md》）后，WorkBuddy 完整配合：`report_session` start/end + `report_tool_call` pre/post 全部 accepted，观察者收到 5 条真实申报事件并正确判定（含 1 条 R010 ALERT）。
> 3. 结论修正：提示词措辞必须**不凌驾 WorkBuddy 自身安全权威**、不宣称强制监测框架，才能同时达成「申报完整率」与「不触发 Agent 拦截」两个目标。

---

## 2. 必要性判断 —— 必要

1. **申报通道的"主动性缺陷"需要补偿**。MCP 申报监测完全依赖 WorkBuddy 主动调用 observer 工具；无任何约束时，Agent 是否申报、申报多完整完全不可控（E2E 文档 E 组用例与 F02 对照即可量化此缺陷）。提示词是当前唯一能在 **不修改 WorkBuddy 内部** 的前提下提升申报完整率的杠杆。
2. **事前约束与事后判定互补**。规则引擎只能"事后看到申报的内容"；提示词可在"事前"引导 Agent 规避危险操作、并在敏感操作前自检，弥补"BLOCK 仅报告层面标记、无真实阻断"的降级缺陷。
3. **合规留痕质量依赖申报质量**。审计日志 / 风险报告的可信度取决于申报事件的完整性（会话边界、pre/post 动作），提示词可明确要求 Agent 申报这些关键节点。

## 3. 可行性判断 —— 可行（附条件）

- 黑盒 Agent 无法修改其内部系统提示词，但 **WorkBuddy 的用户交互界面允许在会话开始输入任意开场提示词**，等价于"用户侧预加载"，无需任何代码改动；
- 提示词只是引导 Agent 调用既有 MCP 工具（`report_session` / `report_tool_call` / `report_action`），与现有语义保护、规则引擎、报告体系天然兼容，不改变任何监测逻辑；
- 附条件：**自动注入**取决于 WorkBuddy 的 MCP 客户端是否支持将 server `instructions` 字段注入上下文——需实验验证；不支持则使用手动粘贴（本方案默认方式）。

## 4. 方案设计

### 4.1 文件存放位置

**统一管理文件夹**：`<项目根>/WorkBuddy降级监测适配/`（与 `observer_sim/` 同级），本次交付文件清单：

| 文件 | 作用 |
|---|---|
| `WorkBuddy降级监测端到端测试用例.md` | 20 条 E2E 用例（含 F02 验证载体） |
| `安全提示词预加载方案.md` | 本文档（方案设计） |
| `安全提示词内容.md` | 提示词全文（直接复制粘贴） |
| `用户使用说明.md` | 用户操作指引 |

**WorkBuddy 如何定位该文件**：

WorkBuddy 是黑盒 Agent，**不直接读取项目文件**，提示词通过以下方式进入其上下文：

1. **默认方式（手动）**：用户打开 `安全提示词内容.md`，复制「提示词开始」与「提示词结束」标记之间的全文，粘贴到 WorkBuddy 会话输入框作为开场消息；
2. **实验方式（自动）**：`python connect_workbuddy.py configure-workbuddy` 写入 WorkBuddy 的 mcp.json 时，observer 条目可附加 `instructions` 字段指向该文件内容；若 WorkBuddy 的 MCP 客户端支持注入 server instructions，则每次会话自动携带，无需手动粘贴；
3. 提示词内容文件与项目代码完全解耦（纯 Markdown 文本），可任意复制、改名、分发，不影响使用。

### 4.2 加载时机（明确触发点）

**明确触发点**：由用户在 **WorkBuddy 交互界面发起开发/代码类任务前** 预加载，具体为——

| 场景 | 是否加载 | 说明 |
|---|---|---|
| 每次在 WorkBuddy **新建会话**，准备发起开发/代码类任务前 | ✅ 必须 | 会话开始的第一条消息即粘贴提示词全文 |
| 会话中途追加新任务 | ✅ 建议 | 若会话上下文较长，重新粘贴一次提示词以强化约束 |
| 涉及命令执行 / 文件读写 / 网络访问 / 权限变更的任务 | ✅ 必须 | 高风险任务无提示词不启动 |
| 纯问答、不触发工具调用的聊天 | ⬜ 可选 | 无申报事件产生，加载与否不影响监测 |
| **MCP 申报监测启动时（daemon start）** | ❌ 不适用 | 见下方说明 |

**为何不在 MCP 申报监测启动时注入**：监测 daemon（observer_sim 侧）与 WorkBuddy 是两个运行期互不耦合的进程，daemon 启动时 **没有任何向 WorkBuddy 上下文写入内容的通道**（设计约束，见 E2E 文档第 3 节"任务输入与监测启停均由测试者手动决定"）。因此加载时机只能落在 WorkBuddy 会话侧（用户粘贴），不可能落在监测启动侧。若要实现"监测启动即注入"，唯一途径是 mcp.json `instructions` 字段（实验方式），其触发点实为"WorkBuddy 读取 mcp.json 连接 observer 时"，同样与 daemon 启停无关。

### 4.3 内容结构（参考 ShellWard 三段式，对齐方寸观察者）

ShellWard `安全提示词.txt` 结构与本方案的映射关系：

| ShellWard 结构 | 本方案对应段落 | 差异说明 |
|---|---|---|
| 系统能力清单（已加载 Skills 与安全策略） | 【第一段 · 身份与申报义务】中的监测环境声明 | 方寸观察者无 Skills 体系，改为声明"MCP 申报通道 + 21 条规则判定"的监测环境与 observer 工具 |
| 安全服务状态确认（调用安全 MCP 工具核查） | 【第一段】申报义务 1（`report_session` 会话边界申报） | 不要求 WorkBuddy 核查观察者状态（黑盒不可靠），改为要求其主动申报会话开始/结束，由观察者侧留痕确认通道连通 |
| 后续行为规范（默认安全 Skill + 敏感操作前核查） | 【第二段 · 行为红线】+【第三段 · 协作约定】 | 红线清单直接映射 `default_policy.yaml` 规则 ID；"敏感操作前核查"改为"先申报 pre 事件 + 向用户确认" |

完整提示词全文见 `安全提示词内容.md`，**v2.0 结构（合规留痕定位，实证有效）**：

```
【一 · 会话留痕】report_session（start/end，agent_id/session_id/session_type/status）
【二 · 工具调用留痕】report_tool_call（pre/post，真实 tool_name/tool_args，失败可重试）
【三 · 动作留痕】report_action（可选，action_type/action/detail）
【四 · 敏感操作提示】涉及破坏性命令/凭据读取/外传/提权前先向用户确认；
                    平台安全策略始终优先于本留痕约定
【五 · 任务结束摘要】回复末尾简述留痕情况（可选）
```

> v1.0 三段式（身份与申报义务 / 行为红线 / 协作约定）中「监测环境声明」「规则 ID 红线清单」「BLOCK 不真实阻断」三类表述在真实 WorkBuddy 会话中触发提示注入判定，v2.0 已删除或弱化；红线清单不再逐条映射规则 ID，改为一句敏感操作提示（WorkBuddy 自身内置安全策略已覆盖事前约束，本提示词不再重复强制）。

### 4.4 与现有安全机制的配合方式

提示词与方寸观察者现有安全机制的分工（**事前 / 事中 / 事后三环**）：

```
事前约束（安全提示词）     →     事中申报（MCP 通道 + SemanticGuard 脱敏）   →   事后判定（default_policy.yaml + 报告）
        │                               │                                        │
  引导 Agent 规避红线操作、         申报流经语义保护（256 字符截断/脱敏）       21 条规则判定 ALLOW/ALERT/BLOCK
  承诺真实完整申报                  → RawEventFactory 统一转换事件             → 风险评分 + 审计留痕 + 风险报告
```

| 现有机制 | 提示词与之的配合方式 |
|---|---|
| `default_policy.yaml` 规则库（21 条） | 提示词第二段红线清单与规则 ID 一一对应，让 Agent **事前** 知道哪些行为会被判 ALERT/BLOCK，从而主动规避；规则库仍独立完成 **事后** 判定，提示词不改变任何规则逻辑 |
| ALERT/BLOCK 判定 | 提示词明确告知 Agent：降级模式下 BLOCK 仅为报告层面标记（无真实阻断），因此 Agent **不得** 依赖"被拦下"来阻止危险操作，必须事前自查 |
| MCP 申报通道（report_tool_call/report_session/report_action） | 提示词第一段规定申报义务与参数规范，直接提升申报完整率与字段质量（真实 tool_name/tool_args），使通道留痕（mcp_reports.jsonl）与判定输入更可信 |
| SemanticGuard 语义保护 | 提示词承诺"申报真实完整"与脱敏机制叠加：即使 Agent 申报含敏感内容，语义保护仍会脱敏/截断，管线安全性不依赖 Agent 自觉 |
| 审计日志 / 风险报告 | 提示词第三段要求任务结束输出申报摘要，便于用户核对审计留痕是否齐全，提升报告可信度 |

**互补关系一句话**：提示词负责 **事前行为约束与申报义务**，MCP 申报监测负责 **事后合规留痕与风险提示**；提示词不替代、不改变任何监测逻辑，仅提升"申报完整率"这一输入端指标。

### 4.5 与端到端测试用例的配合

- **F02 用例** 是本方案的量化验证载体：加载前 / 加载后执行相同任务，比对 `mcp_reports.jsonl` 申报条数与会话边界申报（`report_session`），验证提示词是否提升申报完整率；
- 若 F02 证明有效 → E2E 文档 A~D 组用例的"🔲 测不到（未申报）"项将显著减少，差距清单中"未申报"原因被消除，剩余差距才是监测管线本身的缺口；
- 差距清单据此分为两类改进方向：**申报侧改进**（提示词 / instructions 注入，不碰管线）与 **管线侧改进**（申报字段扩展、跨会话关联、时段基线等，改监测代码），为项目后续迭代提供依据。
